## Question

Is there a repeatable sequence of GitHub Copilot steps and prompts that takes Contoso University from .NET Framework 4.8 to .NET 10, with uploads on Blob, MSMQ replaced by Service Bus, secrets in Key Vault and OpenTelemetry, running on `vm-dev01` against the source database and packaged as an image in a private ACR, within the C3 (1 hour) and C6 (3 hours) time boxes?

## Findings

Run 1, steps 1 (set up) and 2 (assess):

1. **Managed identity trap on `vm-dev01`.** The VM has a system-assigned managed identity, and `DefaultAzureCredential` tries `ManagedIdentityCredential` before `AzureCliCredential`. The app would get the VM's token, which has no data roles, and fail with 403 on Blob, Service Bus and Key Vault. Fix: set the user environment variable `AZURE_TOKEN_CREDENTIALS=AzureCliCredential` on `vm-dev01` only ([Credential chains in the Azure Identity library for .NET](https://learn.microsoft.com/dotnet/azure/sdk/authentication/credential-chains)); the deployed app still uses its managed identity. The owner kept the data roles on the user rather than giving them to the VM identity. In protocol v2, step 1.3.
2. **No git identity for a fresh VM user.** The first commit fails with `Author identity unknown`. Fix: right after `gh auth login`, set `user.name` and a GitHub no-reply `user.email` from `gh api user`, and run `gh auth setup-git` so `git push` uses the gh sign-in. In protocol v2, step 1.2.
3. **Sign-in through Bastion.** Browser sign-in inside the Bastion session is awkward, and passkeys and password managers don't work there. Fix: device code flows (`az login --use-device-code`, and `gh auth login --web` with the code entered at `github.com/login/device`), completed on the attendee's own device. Some tenants block device code flow with Conditional Access. In protocol v2, step 1.2.
4. **The assessment dashboard has no chat and no model picker.** Step 2 ran from the dashboard, so there's no chat export and the model is the extension's default. In protocol v2, recording only asks for chat exports where the owner prompted in Copilot Chat.
5. **The report targets App Service for Windows by default.** The target dropdown defaults to **Azure App Service (Windows)**; the kit targets App Service for Linux (containers) (PRD §2, B09). It has to be switched before **Create Plan**, or the plan targets Windows. The owner re-planned with Linux. In protocol v2, step 2.3; a candidate for a B10 instruction.
6. **Create Plan covers only Cloud Readiness.** **Create Plan (6)** planned the six Cloud Readiness issues: static content, SQL connection, Windows authentication (Mandatory), connection strings, local IO and MSMQ (Mandatory). It did **not** include the .NET 10 upgrade: run 1's first plan (`.github/modernize/ContosoUniversity-20260925073922/plan.md`, commit `7904c1b`) says "No … runtime/framework upgrade", so the upgrade has to be requested explicitly. That's a hot spot for protocol v2 and the B10 playbook. The plan also included **Windows AD to Microsoft Entra ID**; its open questions were Blob or Files and SQL Database or Managed Instance, which the kit answers (Blob, Managed Instance); and its integration verification defaulted to mock mode because no Azure environment was given. The owner sent a correction reply: upgrade first, remove Entra ID, Blob, Managed Instance with local SQL auth kept, order database, Blob, Service Bus, Key Vault, `DefaultAzureCredential` with no keys, App Service for Linux containers, no provisioning. In protocol v2, steps 2.5, 3.2 and 3.3.
7. **False "Windows authentication detected" (Mandatory).** The app has no user sign-in (`BaseController` uses `"System"`, and `FilterConfig` has no `AuthorizeAttribute`). The finding comes only from `<IISExpressWindowsAuthentication>enabled</IISExpressWindowsAuthentication>` (with anonymous authentication disabled) in `ContosoUniversity.csproj` and `Integrated Security=True` in the LocalDB connection string in `Web.config`. It's not applicable, but the first plan included an Entra ID migration for it. The owner removed it. A B10 instruction should say so. In protocol v2, deselect it before **Create Plan** (step 2.4) or remove it in the correction reply (step 3.2).
8. **Planning model:** the plan ran with the `modernize` agent, GPT-6 Sol at reasoning effort Medium (2026-09-25).
9. **"Projects: 1 error"** in the C# Dev Kit status bar on the legacy .NET Framework project before the upgrade is expected.
10. **Create Plan abandoned for the prompt files.** Run 1's first **Create Plan** attempt and its correction chat were stopped. The owner copied `.github/prompts` from the working branch onto `spike/b06-run1` and continued with `/modernize-plan` and `/modernize-execute`, so run 1 also uses the pinned agent and models. Reasoning effort is set in the model picker: Medium for GPT-6 Sol, maximum for GPT-6 Luna.
11. **`reasoning-effort` breaks prompt files.** A `reasoning-effort:` line in the prompt-file frontmatter stopped both prompt files from working in VS Code on `vm-dev01`. The owner removed it (`spike/b06-run1` commit `4508c6d`), and reasoning effort is set in the model picker instead: Sol Medium, Luna maximum.
12. **Slash command didn't run the prompt file** (cause in finding 14). Typing `/modernize-plan` in chat didn't work; opening the prompt file and selecting **▶ Run Prompt** (or **Chat: Run Prompt**) did. Protocol v2 makes **Run Prompt** the primary way, with the slash command as the alternative.
13. **The plan asked which Azure resources to integrate with.** `/modernize-plan` asked "What resource reference should the real-mode integration tests use for the existing Azure environment?", offering subscription and resource group, full resource IDs, or configuration keys supplied at execution time. The owner chose configuration keys, with no identifiers in the plan. The prompt files now say so, and that every resource already exists: at the event, App Service, ACR, SQL MI and the datacenter are deployed for each attendee, so the plan must never provision.
14. **The prompt-file pins may not apply with Run Prompt.** The chat footer in the owner's screenshot showed agent `Agent` and model `GPT-5.6 Sol`, while the file pins `agent: modernize` and `model: ["GPT-6 Sol (copilot)"]`. **Resolved:** the owner was in the Agent Host harness, which doesn't load prompt files. In the Local harness, `/modernize-plan` works and applies the pinned agent. This also explains finding 12. The abandoned Agent Host plan is committed on `spike/b06-run1` as evidence, and the plan was re-run in Local. Protocol v2 step 3.1 says to use the Local harness, and run 2 checks the footer.
15. **Custom assessment, not the default (owner decision).** The default **Start Assessment** defaults to App Service (Windows), which led to the wrong plan target (finding 5). C3 must be a custom assessment with the target set to App Service for Linux (containers). The reset run 1 ran it in the Local harness; the options are in protocol v2 step 2.2 and go into the B11 guides.
16. **Prompt files replaced by skills (owner decision).** The assessment dashboard switches the chat to the Copilot harness, which doesn't load prompt files, so the pinned prompt files didn't run from the natural flow. The owner replaced them with the agent skills `modernize-plan` and `modernize-execute`, which load in both harnesses. Skills can't pin an agent or model, so the owner picks `modernize`, GPT-6 Sol at Medium and GPT-6 Luna at maximum in the chat pickers.

17. **Workspace skills missing from the agent's list.** In the Copilot harness, `modernize-plan` and `modernize-execute` don't appear in the agent's "Available skills" list, which shows only the extension's built-in skills (`assessment`, `create-modernization-plan`, `implementing-code`, `runtime-validation`, `modernization-integration-tests` and others). The files are in the owner's clone. A likely cause is `disable-model-invocation: true`: per [Use Agent Skills in VS Code](https://code.visualstudio.com/docs/agent-customization/agent-skills), it stops the agent from loading a skill by itself and leaves only the `/` slash command, so the skill wouldn't be offered to the model. Whether `/modernize-plan` shows in the slash menu: pending the owner. Meanwhile the owner is running the built-in `/create-modernization-plan` with the `modernize-plan` SKILL.md body as its input. Protocol v2 step 3 is decided after that result.
18. **Dashboard as the primary path (owner decision).** The owner chose the dashboard buttons for attendees: custom assessment, **Create Plan** from the report, then execute. They write the prompts, so no skill or prompt file is needed. The risk is that each button runs with whatever agent and model are selected, so protocol v2 puts a ⚠️ check before each one. The review checklist and the inlined correction reply cover what **Create Plan** misses (findings 5–7). The workspace skills were removed.
19. **The .NET upgrade agent isn't installed (owner decision: no change).** Learn says the `modernize` agent hands .NET version upgrades to GitHub Copilot upgrade. In VS Code that's a separate extension, `ms-dotnettools.upgrade-agent` (1.1.539, preview, not deprecated), which `vscjava.migrate-java-to-azure` doesn't bundle: it depends only on Copilot Chat. That likely explains "No … runtime/framework upgrade" in the **Create Plan** output (finding 6). The owner decided to keep the kit on the modernization extension only, with the .NET 10 upgrade added through the plan review and correction reply (protocol v2 step 3.3). If the upgrade step proves unreliable, installing the upgrade extension is the option for B10 and B13.
20. **Run 1's dashboard plan still has no upgrade** (commit `e5defe5`, `.github/modernize/contoso-university-azure-services-modernization`). Even from the custom assessment with the Linux target, **Create Plan** says "No runtime/framework upgrade is included because none was requested". That matches finding 19: the upgrade agent isn't installed.
21. **Windows authentication is easy to leave selected.** The plan includes task 005, Windows AD to Entra ID, because Windows authentication wasn't deselected before **Create Plan**. Protocol v2 now has a second ⚠️ callout, as loud as the model check (step 3.2).
22. **Create Plan chains both alternatives.** It kept 001 Blob, 002 Azure Files, 003 Azure SQL Database and 004 Azure SQL Managed Instance in sequence, and put the upload task 007 on `migration-azure-storage-mount` (Azure Files). Executed as is, both alternatives would be applied. It also had no local SQL auth rule, no hosting target ("No deployment target is assumed") and no rule against keys. The correction reply (protocol v2 step 3.4) removes 002, 003 and 005, moves 007 to Blob, adds the upgrade first and orders Managed Instance, Blob, Service Bus, Key Vault, then the CVE check.
23. **The plan uses the extension's built-in skills:** `migration-azure-storage-blob`, `migration-managed-identity`, `migration-azure-sql-database`, `migration-microsoft-entra-id`, `migration-azure-keyvault-secret` and `migration-azure-servicebus`. Input for B10: the playbook can name these rather than write its own.
24. **Chat: Export Chat failed.** The JSON export didn't work, so the owner pasted the chat into `chats/run1-step3-plan.txt`. Protocol v2 allows `.txt` exports. Checked for secrets, IDs and tokens: none.

## Decisions

- **Dashboard buttons as the primary path (owner decision, 2026-09-25).** Steps 2 and 3 use the modernization dashboard: a custom assessment targeting App Service for Linux (containers), **Create Plan** from the report with Windows authentication deselected, then execute. Each button uses whatever agent and model are selected in the Chat panel, so a ⚠️ callout before each one says what to select: `modernize` with GPT-6 Sol at Medium to plan, GPT-6 Luna at maximum to execute. The plan is reviewed against a checklist, and a correction reply inlined in the protocol fixes gaps. Prompt files and then agent skills were tried first and dropped (findings 10–17). [B06](../../backlog/B06-spike-ghcp.md) requirement 7 still leaves the model unpinned; it now says the protocol names what to select before each button.
