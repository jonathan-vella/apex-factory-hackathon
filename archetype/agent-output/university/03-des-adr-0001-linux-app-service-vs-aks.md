## 🔍 Context

> “The workload is a single-region, single-environment N-tier platform: a Linux container web app on App Service, a private ACR, SQL Managed Instance, Blob storage, a Service Bus queue, Key Vault and Application Insights.”

Requirements > Complexity Classification records the platform as `standard`: more than eight resource types, but single region, single environment and built-in policies only, with cross-subscription discovery and existing-spoke constraints. The approved service list has no Kubernetes runtime, and the training/demo audience is fewer than 50 users. The decision is whether to run the web tier on Linux App Service now or on AKS. AKS is a future archetype, not a Step 2 design.

## ✅ Decision

Use Linux App Service for the current workload and keep AKS as the future archetype to revisit only if workload scale, custom orchestration, or multiple isolated services require it.

## 🔄 Alternatives Considered

| Option | Pros | Cons | WAF Impact |
| --- | --- | --- | --- |
| Linux App Service (selected) | Approved user-pinned SKU (P0v3) with regional VNet integration verified; no cluster to operate | Less runtime control than a cluster | Priced in Step 2 (plan $64.97/month); other pillars qualitative |
| AKS now | More runtime control for multi-service orchestration | Adds cluster, node, ingress and identity design that Steps 1-2 did not assess | Not assessed: no AKS topology or price exists |

## ⚖️ Consequences

### Positive

- No cluster, node pool or ingress layer to design or operate for a single web application (qualitative).
- The app still pulls images from the private ACR and uses VNet integration with the private-endpoint model.

### Negative

- The platform is not optimized for highly distributed microservice orchestration.
- A later AKS transition would require rework and a separate operational maturity review.

### Neutral

- The comparison is intentionally scoped to the currently approved workload, not a generic future state.

## 🏛️ WAF Pillar Analysis

Arrows are qualitative judgements for the selected option against the AKS alternative, not Step 2 scores: ↑ improves the pillar, → is neutral, ↓ weakens it. "Not assessed" means Steps 1-2 hold no evidence.

| Pillar | Impact | Notes |
| --- | --- | --- |
| Security | ↑ | App Service removes a cluster as an attack surface. It does not remove the four private PaaS endpoints or their policy-driven DNS readiness duties. The public HTTPS front end still has no WAF and no end-user authentication; both were excluded from B09, and end-user authentication is owned by B06/B10. Those are residual scope constraints, not benefits of this choice. |
| Reliability | Not assessed | App Service facts only: single P0v3 instance, no zone redundancy, best-effort (ADR-0007). No AKS availability design exists to compare. |
| Performance | Not assessed | No AKS performance comparison exists; fewer than 50 users describes current demand, not comparative evidence. |
| Cost | Not assessed | The plan is priced at $64.97/month; no AKS design or price exists to compare. |
| Operations | ↑ | No cluster to operate, upgrade or secure (qualitative). |

## 🔒 Compliance Considerations

- This decision stays inside the approved shared-services model and private-link policy posture.
- The current design remains compatible with the private-network and hub-firewall controls already captured in the architecture assessment.
- AKS is not treated as a current requirement and therefore does not add extra posture or policy obligations during this phase.

## 📝 Implementation Notes

- Current deployment target: App Service on Linux with a container image pulled from the private ACR.
- Keep AKS in a future-state backlog only if new runtime or scale needs are proven by evidence.
- This ADR is intentionally narrow: it does not alter the approved platform boundary or any network policy decision.
