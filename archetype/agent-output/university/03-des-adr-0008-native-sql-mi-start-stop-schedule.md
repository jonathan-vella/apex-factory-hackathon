## 🔍 Context

> “The native SQL MI stop/start schedule replaces Automation or a Logic App: no extra resource or runbook. It takes effect only after C7 removes the MI link.” (02-architecture-assessment.md)

The assessment fixes the window at Mon-Fri 07:30-18:30 `W. Europe Standard Time`, with a `timeZoneId` parameter. Microsoft Learn lists instances that use the Managed Instance link or have zone redundancy enabled as instances that cannot be stopped ([Stop and start an instance](https://learn.microsoft.com/azure/azure-sql/managed-instance/instance-stop-start-how-to)), which is why the schedule is gated on C7 and tied to ADR-0007. The decision is whether to use the native schedule or an external automation.

## ✅ Decision

Use the native SQL MI start/stop schedule (one free `Microsoft.Sql/managedInstances/startStopSchedules` child resource) with the approved weekday window, instead of Automation or a Logic App.

## 🔄 Alternatives Considered

Arrows are qualitative: ↑ improves the pillar, → is neutral, ↓ weakens it.

| Option | Pros | Cons | WAF Impact |
| --- | --- | --- | --- |
| Native schedule (selected) | No separate Automation or Logic App resource, runtime identity or runbook; one free child resource | Blocked until C7 removes the MI link; SQL MI is unavailable outside the window | Cost Optimization ↑, Operations ↑, Reliability ↓ |
| Automation or Logic App | More flexible schedules than the built-in scheduler allows | Adds a resource, an identity and a runbook | Operations ↓, Security ↓ |
| No schedule | Simplest; SQL MI always on | Gives up post-C7 savings (AHB $174.61/month scheduled vs $488.92 at 730 h) | Cost Optimization ↓ |

## ⚖️ Consequences

### Positive

- Avoids a separate Automation or Logic App resource, runtime identity and runbook.
- Matches the cost model: $174.61/month scheduled after C7 against $488.92 at 730 h, both with AHB.

### Negative

- The schedule only applies after C7, so there are no savings before cutover.
- Once enabled, SQL MI is stopped outside the window and dependent requests fail until it is started. Learn: starting an instance "takes about 20 minutes from the moment the start operation is initiated", so after the 07:30 entry initiates the start, SQL MI is not available for about 20 minutes.
- No backups are taken while stopped, and maintenance notifications are not sent for a stopped instance (Learn).

### Neutral

- This outcome is tied to the later architecture state and not a current code change outside the platform schedule.

## 🏛️ WAF Pillar Analysis

| Pillar | Impact | Notes |
| --- | --- | --- |
| Security | → | No new privileged resource is introduced, so the security boundary stays clean. |
| Reliability | ↓ | After C7, SQL MI is stopped outside the window and dependent requests are unavailable until it is started. |
| Performance | → | Not assessed; a stop clears cached data (Learn). |
| Cost Optimization | ↑ | Compute and licence are not billed while stopped; storage and backup still are (Learn). |
| Operations | ↑ | Native scheduling needs no separate automation to maintain. |

## 🔒 Compliance Considerations

- The schedule is an owner-requested cost-control and operations choice, not a compliance control. It stays consistent with the post-C7 state, where the MI link and zone redundancy are both absent.
- No additional runbook or automation resource without a fresh architecture review.

## 📝 Implementation Notes

- Deploy `startStopSchedules@2025-01-01`, name `default`, one entry per weekday Mon-Fri 07:30-18:30, `timeZoneId` as a parameter, enabled after C7.
- Scheduled start and stop operations are not recorded in the Activity Log (Learn), so verify behaviour from SQL MI state.
- Re-evaluate if the MI link or workload timing changes.
