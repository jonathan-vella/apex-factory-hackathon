## 🔍 Context

> “To import to or from a network-restricted Azure container registry, the restricted registry must allow access by trusted services to bypass the network.” ([Microsoft Learn: Import container images](https://learn.microsoft.com/azure/container-registry/container-registry-import-images))

Requirements capability 4 sets `publicNetworkAccess: Disabled` with `networkRuleBypassOptions: AzureServices` for `az acr import` of the known-good image. The assessment records the exception as “owner-accepted, test-gated”. Learn adds that a registry with a private endpoint that does not enable the setting fails import.

## ✅ Decision

Set `networkRuleBypassOptions: AzureServices` on the private ACR, with `publicNetworkAccess: Disabled`, so `az acr import` works. The setting is registry-level and stays in place. The post-deployment import test gates readiness; it does not narrow or remove the bypass.

## 🔄 Alternatives Considered

| Option | Pros | Cons | WAF Impact |
| --- | --- | --- | --- |
| Trusted-services bypass (selected) | Enables `az acr import` with public access disabled | Registry-level exception for trusted Azure services, not only import; stays set after the test | Security ↓ (accepted), Reliability ↑ |
| No bypass, no import | Strictest network posture | Import fails; the private-image path cannot be proved end to end | Security ↑, Reliability ↓ |
| Public ACR access as fallback | Simplifies import testing | Violates the approved private-only model | Security ↓, non-compliant |

## ⚖️ Consequences

### Positive

- Makes the private-registry image import path actually achievable.
- Preserves the private ACR posture while allowing a controlled import workflow.

### Negative

- The registry network rule set is widened at registry level, not for the import operation only, and stays widened after the test.
- Any import failure must be treated as a deployment readiness issue, not as a harmless side effect.

### Neutral

- `publicNetworkAccess` stays `Disabled`. The bypass is not a public endpoint, but it is a persistent network-rule exception.

## 🏛️ WAF Pillar Analysis

| Pillar | Impact | Notes |
| --- | --- | --- |
| Security | ↓ | Registry-level trusted-services exception that persists after the test; owner-accepted. `publicNetworkAccess` stays `Disabled`. |
| Reliability | ↑ | Supports the private image import and the later switch to the registry copy without a public fallback. |
| Performance | → | Not assessed; no image-startup or throughput rationale. |
| Cost | → | No significant cost delta beyond the premium registry model itself. |
| Operations | ↑ | The design adds explicit validation and readiness checks, reducing hidden failure modes. |

## 🔒 Compliance Considerations

- The design stays consistent with the private-only registry requirement and the shared landing-zone policy posture.
- The bypass is not a public endpoint, but it is a registry-level exception for trusted Azure services and is not limited to the import operation. The post-deployment import test must pass before the import capability is claimed.
- It must remain gated behind post-deploy readiness checks and no public workaround.

## 📝 Implementation Notes

- Set the bypass on the registry in IaC; it stays set unless a later step disables it. The deployer needs `Container Registry Data Importer and Data Reader`.
- Validate the registry import and the private web-app pull path before declaring the workload ready.
- If the import check fails, stop and treat it as a deployment blocker rather than widening public access.
