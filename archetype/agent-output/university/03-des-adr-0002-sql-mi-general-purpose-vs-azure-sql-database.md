## 🔍 Context

> “SQL MI is VNet-injected, Entra-only, with the public data endpoint off.” (02-architecture-assessment.md)

Requirements capability 5 makes “SQL Managed Instance as migration target” a Must: “MI in `snet-sqlmi`, `databaseFormat`/engine set to `SQLServer2022` explicitly, Entra-only, reachable on VNet-local host name”.

Owner-stated topology (B07/B08; not recorded in the Step 1-3.5 artifacts): the MI link runs from `vm-app01` (SQL Server 2022, in the datacenter) through the hub firewall to `snet-sqlmi`, over TCP 5022 and 11000-11999. The assessment states that the stop/start schedule is blocked while the link is active, before C7. Choosing Azure SQL Database would require changing capability 5.

## ✅ Decision

Keep SQL Managed Instance General Purpose as the operational database pattern and treat Azure SQL Database as a future simplification only if the MI link and managed-instance operational constraints are intentionally retired.

## 🔄 Alternatives Considered

| Option | Pros | Cons | WAF Impact |
| --- | --- | --- | --- |
| SQL MI General Purpose (selected) | Meets capability 5 and the MI-link migration path; VNet-injected with the public data endpoint off | Runs 24x7 until C7 because the MI link blocks the schedule | Priced in Step 2 (AHB, 730 h: $488.92/month compute and licence) |
| Azure SQL Database | Not assessed: no comparable design, price or availability objective in Steps 1-2 | Would require changing capability 5 | Not assessed |
| SQL MI Business Critical | Not assessed | Not priced or sized in Step 2; stop/start is available only on General Purpose ([Microsoft Learn](https://learn.microsoft.com/azure/azure-sql/managed-instance/instance-stop-start-how-to)) | Not assessed |

## ⚖️ Consequences

### Positive

- Aligns with the approved MI-link migration and spoke networking pattern.
- Keeps the database inside the same private network posture as the rest of the workload.
- The native start/stop schedule (ADR-0008) becomes usable on General Purpose once C7 removes the MI link.

### Negative

- SQL MI runs 24x7 until C7, so schedule savings do not materialize before cutover (assessment risk table).
- More to operate than a single-database PaaS service (qualitative; not compared).

### Neutral

- A later database simplification remains an option only after the MI link path is intentionally retired.

## 🔒 Compliance Considerations

- The design remains Entra-only and keeps the public data endpoint off, consistent with the approved governance constraints and private-link standards.
- The start/stop schedule (ADR-0008) is an owner-requested cost-control and operations choice, not a compliance control. It is ineffective while the MI link is active; savings begin only after C7.
- A future Azure SQL Database path would require explicit review and a new migration decision based on broader workload requirements.

## 📝 Implementation Notes

- Keep SQL MI General Purpose in `snet-sqlmi`. The IaC creates no NSG or route; vending owns `nsg-sqlmi` and `rt-sqlmi`.
- MI link path (owner-stated, B07/B08): `vm-app01` (SQL Server 2022, datacenter), through the hub firewall, to `snet-sqlmi`, TCP 5022 and 11000-11999.
- Treat the platform as a managed-instance migration, not a move to Azure SQL Database.
- This ADR does not waive the need to document the final migration cutover if the workload later moves to Azure SQL Database.
