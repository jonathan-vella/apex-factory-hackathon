## How you work with one repo and one dev container

- **One repo of your own.** A private repo created from the [`apex-accelerator`](https://github.com/jonathan-vella/apex-accelerator) template. It brings the **APEX agents**, Copilot custom agents that appear in Copilot Chat's agent picker.
- **One dev container.** A ready-made Linux workspace that VS Code opens inside Docker, so every member has the same tools: Azure CLI, PowerShell 7, Git, `azd` and Bicep.
- **One import.** A single command copies the kit into a `factory/` folder in your repo. You run every script from `factory/`, inside the dev container.
- **One exception.** `vm-dev01`, which you set up in C0 task 7. From C3 the app work happens there (C3, C6, C7 and C9). C4, C5 and C10 run in the dev container again, and C8 uses both. Each challenge page has a **Where to run** block.
- **Evidence** lives in your own repo, under `factory/evidence/` ([C1](../../challenges/c01-define-the-opportunity/#where-your-evidence-goes) sets it up). There is no shared team repo. After the merge below, all your work is on `main`, except the `vm-dev01-work` branch on `vm-dev01`, which you never merge.

The event is for partner infrastructure architects and engineers, in teams of three to five. Each team has its own Microsoft Entra tenant and a platform lead. You don't need to be a .NET or SQL Server specialist, because the application and database work is GitHub Copilot-assisted. The exams come after the event: see the [Partner learning path](../../guides/learning-path/).

## How you deploy

You deploy with GitHub Actions. You set it up once, then run each stage from your own repo and walk away. Every run leaves a log. In C0 you deploy your datacenter. The platform lead also deploys the foundation and connects every member. [Deploy with GitHub Actions](../../guides/deploy-with-actions/) has the steps.

It needs what this page sets up: your repo with the kit merged to `main` (GitHub runs a workflow only from the default branch), a signed-in `az` and `gh`, and your settings file. You don't install anything else: the dev container has every tool.

## Install on your machine

You only need these host tools to open the dev container. Everything else, including the Azure CLI, is inside it.

| Tool | Why | Verify |
| --- | --- | --- |
| [VS Code](https://code.visualstudio.com/) 1.100 or newer | The editor, agent mode, and **Git: Clone** | `code --version` |
| [Docker Desktop](https://www.docker.com/products/docker-desktop/) | Runs the dev container | `docker version` |
| [Git](https://git-scm.com/downloads) | VS Code's **Git: Clone** needs it | `git --version` |
| VS Code extensions: Dev Containers (`ms-vscode-remote.remote-containers`), GitHub Copilot Chat (`github.copilot-chat`) | Open the container; Copilot sign-in | `code --list-extensions` |

```powershell
code --install-extension ms-vscode-remote.remote-containers
code --install-extension github.copilot-chat
```

### Windows 11 from scratch

<Steps>

1. Install [WSL](https://learn.microsoft.com/windows/wsl/install) with Ubuntu (`wsl --install`), then restart. Open **Ubuntu** from the Start menu once: the first launch asks you to create a Linux user name and password.
2. Install Docker Desktop and turn on **Use the WSL 2 based engine**. Then open Docker Desktop **Settings** > **Resources** > **WSL integration** and switch on **Ubuntu**. Without this, the dev container can't find Docker from Ubuntu.
3. Install VS Code, the two extensions above, and the **WSL** extension (`ms-vscode-remote.remote-wsl`).
4. You clone your repo from inside Ubuntu (next step), not into a Windows folder: the dev container is much faster that way, and line endings stay correct.

</Steps>

### Network

Allow outbound HTTPS to these hosts:

- **GitHub and Copilot:** `github.com`, `api.github.com`, `codeload.github.com`, `*.githubusercontent.com`, `api.githubcopilot.com`.
- **Azure and Microsoft:** `*.azure.com`, `*.microsoft.com`, `login.microsoftonline.com`, `learn.microsoft.com`.
- **Docker Hub:** `docker.io`, `registry-1.docker.io`.
- **The dev container:** `ghcr.io` (its features come from there), `mcr.microsoft.com` (its base image, covered by `*.microsoft.com`) and `packagefeedproxy.microsoft.io` (its Node.js and Python package proxy).
- **VS Code:** `marketplace.visualstudio.com` for extensions.

## Create your repo and import the kit

<Steps>

1. **Create the repo.** Open the [`apex-accelerator`](https://github.com/jonathan-vella/apex-accelerator) template, choose **Use this template** > **Create a new repository**, set the owner to your partner org, and make it **Private**. Add your coach as a collaborator (**Settings** > **Collaborators**) so they can read your evidence.

   :::caution[Ignore the template's own README]
   Your new repo opens on the template's README and its Quick Start. Follow this page instead. From that README you need only the dev container (steps 2 and 3 here). **Don't run** `npm run setup`, **don't** change the Actions pull request permission, and **don't** run the Weekly Maintenance or Governance Policy Baseline workflows: the kit doesn't use them. The template's scheduled workflows may show failed runs on Mondays: ignore them. If you work for Microsoft and the container build fails on package feeds, start VS Code with the template's `.devcontainer/open-microsoft.ps1` launcher.
   :::

2. **Clone it with VS Code.** On Windows 11, press `F1` > `WSL: Connect to WSL` first, so VS Code runs inside Ubuntu. Then press `F1` > `Git: Clone`, choose **Clone from GitHub**, sign in when asked, pick your repo and a folder in your home folder, and choose **Open**.

3. **Reopen in the dev container.** Choose **Reopen in Container** when VS Code offers it (or press `F1` > `Dev Containers: Reopen in Container`). The first build takes about 10 minutes. It's done when a terminal prompt appears. If it fails, see [Troubleshooting](../../reference/troubleshooting/#prerequisites).

4. **Import the kit.** In the dev container terminal, at the repo root, paste these three lines as they are:

   ```bash
   curl -fsSLO https://raw.githubusercontent.com/jonathan-vella/apex-factory-hackathon/main/scripts/Import-Kit.ps1
   pwsh ./Import-Kit.ps1
   rm Import-Kit.ps1
   ```

   This creates `factory/` and imports the CoE archetype's APEX project into the repo root.

5. **Set your git identity, once.** A new dev container has none, and the commit fails with "Author identity unknown" without it.

   ```bash
   git config --global user.name "<your name>"
   git config --global user.email "<your email>"
   ```

6. **Commit the import to a new branch, never to `main`.** If Copilot Chat asks you to sign in, use the Accounts menu at the bottom left of VS Code. Then paste this prompt into Copilot Chat in Agent mode:

   ```text
   Commit and push all my changes to a new branch. Do not use the apex-git-commit skill or its path exclusions: I want every change committed, including agent-output/, infra/ and factory/.

   1. Run `git status --short`. If the current branch is main, create and switch to a new branch named feat/<two or three words describing the changes>. Otherwise stay on the current branch.
   2. Stage everything with `git add -A`.
   3. Commit with a conventional message, type: Subject (types: feat, fix, docs, chore), for example `chore: Import the factory kit`. The repo's hooks run on commit.
   4. If a hook fails, read its output and fix the cause if it is in a file you changed, then commit again. The one exception: if the only failing hook is iac-security-baseline and it reports only these two findings, retry once with `LEFTHOOK_EXCLUDE=iac-security-baseline git commit ...`:
      - keyvault.bicep: purge protection must be enabled
      - web-app.bicep: public network access
      Those two are accepted lab risks in the archetype (purge protection stays off so the lab can be torn down, and the web app is public on purpose). Do not edit the Bicep to silence them. For any other failure, stop and show me the output.
   5. Never use --no-verify, never force-push, and never commit to main.
   6. Push with `git push -u origin <branch>`, then show me the commit hash, the branch name and the number of files committed.
   ```

</Steps>

Done when `ls factory` lists `scripts`, `infra`, `app`, `db`, `templates` and `archetype`, and your `feat/...` branch and its commit are on GitHub.

<details>
<summary>If the import or the commit fails</summary>

- The import refuses to overwrite an existing `factory/` unless you add `-Force`. If a run fails, the third line has already deleted the script, so repeat all three lines, and add `-Force` to the second one (`pwsh ./Import-Kit.ps1 -Force`) when the script says `factory/` exists. `-Force` replaces only the kit folders: it keeps `factory/.local/` (your settings and datacenter credentials) and your archetype work. Add `-ReplaceArchetype` only if you want the kit's archetype copy back and accept losing your changes to it.
- If you commit by hand, run `git switch -c feat/import-kit` first and check that `git branch --show-current` does not print `main`. Don't use `/apex-git-commit`: it skips `agent-output/` and `infra/`, which hold the imported archetype.
- The import keeps `factory/` out of the repo's linters and the weekly upstream sync, and excludes the imported archetype (`infra/bicep/university`) from the template's `iac-security-baseline` hook, because its two accepted lab findings would otherwise block every commit that touches it. If the hook still blocks a commit that only touches the archetype, re-run the import with `-Force`, or use the prompt's exception.
- The archetype was built against APEX commit `c209d8b` (recorded in `archetype/README.md`). If the APEX agents behave differently from the C5 instructions, tell your coach.

</details>

## Sign in and create your settings file

<Steps>

1. **Start PowerShell.** The dev container terminal starts in bash.

   ```bash
   pwsh
   ```

2. **Sign in to Azure.** Find your **tenant ID** (Azure portal, **Microsoft Entra ID** > **Overview**) and your **subscription ID** (**Subscriptions**). `az login` prints a code: enter it at `microsoft.com/devicelogin` in a browser on your own computer.

   ```powershell
   az login --tenant '<tenant-id>' --use-device-code
   az account set --subscription '<subscription-id>'
   az account show --output table
   ```

   Check that `az account show` prints your workload subscription, and compare its **subscription ID** with the portal, not the name: the CLI caches names. If `--use-device-code` is blocked in your tenant, run `az login --tenant '<tenant-id>'` and finish in the browser.

3. **Sign in to GitHub.** Choose **GitHub.com**, **HTTPS** and **Login with a web browser**. `gh` prints a one-time code: enter it at `github.com/login/device`.

   ```powershell
   gh auth login --hostname github.com --git-protocol https --web
   gh auth setup-git
   ```

4. **Create your settings file.** Run it from `factory/`.

   ```powershell
   cd factory
   ./scripts/Initialize-Settings.ps1
   ```

   It asks for your tenant ID and workload subscription ID (it offers the ones from your `az login`), your member index, your location (press Enter for `swedencentral`) and the shared services subscription. It shows the subscription name it is about to save: answer `Y` only when that name is yours.

5. **Check your vCPU quota.**

   ```powershell
   az vm list-usage --location swedencentral --output table
   ```

   For the rows `Total Regional vCPUs` and `Standard Dasv6 Family vCPUs`, `CurrentValue + 16` must be no larger than `Limit`. If not, ask for a quota increase under **Usage + quotas** and tell your coach.

6. **Send the event owner your roster values** once preflight is green (C0 task 1). Use the private event channel, never a repo or issue. They are your workload subscription ID (`$s.subscriptionId`), member index (`$s.memberIndex`), Entra object ID (`az ad signed-in-user show --query id -o tsv`) and work email. The platform lead needs them to connect you at T-1.

</Steps>

Done when `Get-Content .local/settings.json` shows `tenantId`, `subscriptionId`, `location`, `memberIndex` and `suffix`, and the quota check passes. `factory/.local/` is git-ignored, so your IDs never go to GitHub. Run every script from the `factory/` folder.

<details>
<summary>About the settings questions</summary>

- **Member index:** the event owner assigns you a number from 1 to 20, unique within your team, and your coach relays it. Ask your coach if you don't have one; don't pick your own. It isn't the six-character suffix the script generates. Later pages show these as `$s.memberIndex` and `$s.suffix`, read from `factory/.local/settings.json`.
- **Shared services subscription, members:** press Enter to skip it. The platform lead shares its ID when they connect you at T-1, and you add it with `./scripts/Initialize-Settings.ps1 -SharedSubscriptionId '<shared-services-subscription-id>'` (C2 task 1). Re-running never changes your other values.
- **Shared services subscription, platform lead:** enter it now. The script prints its name on a `Shared:` line: check it is your shared services subscription and not another one you own. Preflight then also checks your Tenant Root rights, so a missing role shows up at T-14 and not at T-7.
- **Wrong subscription name:** `az account list --refresh --output table` updates the cached names. `Initialize-Settings.ps1` can't tell a mistyped but valid ID from a real one, so read the name it shows.

</details>

## Merge your import into main

Your import is still on the `feat/...` branch. Merge it, so `main` holds the kit and everything that follows can run on `main`.

<Steps>

1. On GitHub, open your repo. Choose **Compare & pull request** for the `feat/...` branch (or **Pull requests** > **New pull request**), then **Create pull request**, **Merge pull request** and **Confirm merge**. This is the only branch you merge into `main`. If a rule blocks the merge, tell your coach.
2. In the dev container, bring `main` up to date:

   ```powershell
   git switch main && git pull
   ```

</Steps>

Done when `factory/` is visible on `main` on GitHub and `git branch --show-current` prints `main`.

From now on, all your work is on `main`, except the `vm-dev01-work` branch that C0 sets up on `vm-dev01`. Evidence follows one rule everywhere:

- **Dev container:** evidence goes in `factory/evidence/` on `main`; run `git pull` first.
- **`vm-dev01`:** evidence goes in `C:\src\<your-repo>\factory\evidence\...` (the plain clone of your own repo) on `main`; run `git pull --rebase` first.

Each member keeps evidence in their own repo. For a team document, one person types it, then every teammate saves the final file under the same name in their own `factory/evidence/cNN/`.
