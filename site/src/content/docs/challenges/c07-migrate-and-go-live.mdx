## Background

This is the go-live. You move the database to SQL Managed Instance with no data loss, then put the modernized app live on App Service against it.

**Business context.** Marcus, the registrar, runs the office that can't stop enrollment for long. C7 moves the database and puts the app live, with a planned stop he can warn his staff about.

**Business outcome.** Safe, repeatable change. The move is a planned cutover with a written rollback, and the stop for the registrar's office is as short as the team can make it. Illustrative target: under an hour.

**Objective.** Be able to migrate a database online with the MI link, validate the replica, cut over safely, and bring the app up on the new platform.

**Time and scope.** Day 2, **08:30** link setup and **10:30** go-live window, **120 min**, **Member**. Pacing: requirements 1 to 3 about 25, requirement 4 about 25, requirements 5 and 6 about 30, requirement 7 about 5 and requirement 8 about 10. The rest is slack.

## Challenge

The MI link is a database mirror from `vm-app01` to your managed instance. It keeps a read-only copy in sync until you cut over, and then the managed instance takes over as the live database.

### Fixed by the kit

The datacenter deployment turned on availability groups on `vm-app01`'s SQL Server, set the startup trace flags `-T1800` and `-T9567`, made `NT AUTHORITY\SYSTEM` a sysadmin and onboarded the instance to Azure Arc (the readiness check). Vending opened the network path between `vm-app01` and your managed instance's subnet. Requirement 1 does the rest of what the link needs on the source: a Windows Firewall rule for port 5022, a database master key, the Azure root certificates and a full backup.

## Requirements

1. **Prepare the source.** <span class="sl-badge caution">vm-app01 · Admin PowerShell</span> Run the kit's `Prepare-MiLinkSource.ps1` on `vm-app01`. It must run inside a Bastion session, because VM run commands stop working once the VM is Arc-enabled. Safe to run again: it adds what's missing, resets the firewall rule's source address and takes a new full backup.

   1. Connect to `vm-app01` through Bastion and open an Administrator Windows PowerShell.
   2. Download the script and run it with the command printed on `vm-dev01` above, which has your `<n>` in it (when `<n>` is `256` or higher, use the exact `-MiSubnetPrefix` printed above). If your event runs from a copy of the kit, your coach gives you that copy's URL instead of the one below.

      ```powershell title="vm-app01 — Administrator Windows PowerShell"
      [Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
      New-Item -ItemType Directory -Force C:\LabTools | Out-Null
      Invoke-WebRequest -Uri 'https://raw.githubusercontent.com/jonathan-vella/apex-factory-hackathon/main/infra/datacenter/scripts/Prepare-MiLinkSource.ps1' -OutFile C:\LabTools\Prepare-MiLinkSource.ps1 -UseBasicParsing
      C:\LabTools\Prepare-MiLinkSource.ps1 -MiSubnetPrefix 10.20.<n>.128/26
      ```

   The script prints one line per step with the time, and logs the same lines to `C:\LabTools\logs\Prepare-MiLinkSource.log`. You should see, in order: the firewall rule for TCP 5022; an `Instance:` line with availability groups `1`, trace flags on `2 of 2` and SYSTEM sysadmin `1`; the database master key created (or "exists"); the two root certificates `DigiCertPKI` and `MicrosoftPKI` imported (or "exist"); `ContosoUniversity` in the full recovery model; the full backup with checksum; and last, `The source is ready for MI link.`

   **Expected result:** The last line is `The source is ready for MI link.`

   **If it fails:** If you see an `ERROR:` line, see **If link creation fails** in the hints.
2. **Start the link.** <span class="sl-badge tip">Azure portal</span> Start the MI link migration against your SQL Managed Instance.

   1. Open **Azure Arc** > **SQL Server instances** and select the instance whose host machine is `vm-app01`. In the menu, under **Migration**, select **Database migration**. The pane has four tiles: **Assess source instance**, **Select target**, **Migrate data** and **Monitor and cutover**.
   2. **Select target**: on the **Create or select target** pane, choose **Yes, I have already created a target**. Pick your workload subscription, the resource group `rg-university-<suffix>` and the managed instance `sqlmi-university-<suffix>`, then select the target.
   3. **Migrate data** > **Migrate using real-time replication (online)**. (**Migrate using log shipping (online)** is a different method that the kit doesn't use.)
   4. Tick `ContosoUniversity` and select **Next: Settings**. Name the link and leave the generated availability group name. **Test connection** can pass even when creation would fail, so don't treat it as proof.
   5. Select **Next: Review + create**. Read each warning. A warning that leaves **Start data migration** available doesn't block you; one that blocks it, or that mentions the network, certificates or backups, means stop and see **If link creation fails**.
   6. Select **Start data migration** and note the time. Follow it in **Monitor migrations** (the **Monitor and cutover** pane): creating the link takes up to 10 minutes, then it seeds the database.

   Continue C6 while creation and seeding run. Done when the status of `ContosoUniversity` is **Ready for cutover**. The **Lag** column shows two dashes, which Microsoft Learn describes as no lag.
3. **Validate the read-only replica.** <span class="sl-badge note">vm-dev01 · SSMS</span> Finish C6 and confirm the link is **Ready for cutover** before starting this validation. The replica must hold the same data as the source before you trust it. In SSMS on `vm-dev01`, open two connections:

   - **Source:** server name `10.10.<n>.4` (or the `Source SQL Server address` printed above when `<n>` is `256` or higher); **Authentication** SQL Server Authentication; **Login** `contosoapp` with the password printed on `vm-dev01` above. Select **Options** > **Connection Properties** and tick **Trust server certificate**, because the source's certificate is self-signed.
   - **Replica:** server name the host name that `$mi` printed (paste it); **Authentication** **Microsoft Entra MFA**; **User name** the account that deployed the archetype in C5.

   On each connection, open a new query on the `ContosoUniversity` database and run these, with no writers on the source (stop anything you started in C6):

   ```sql title="vm-dev01 — SSMS (run on both Source and Replica connections)"
   -- 1. Row counts of every table
   SELECT s.name + N'.' + t.name AS TableName, SUM(p.rows) AS [RowCount]
   FROM sys.tables AS t
   JOIN sys.schemas AS s ON s.schema_id = t.schema_id
   JOIN sys.partitions AS p ON p.object_id = t.object_id AND p.index_id IN (0, 1)
   GROUP BY s.name, t.name
   ORDER BY TableName;

   -- 2. A content checksum of two tables
   SELECT COUNT(*) AS Total, CHECKSUM_AGG(BINARY_CHECKSUM(*)) AS Fingerprint FROM dbo.Department;
   SELECT COUNT(*) AS Total, CHECKSUM_AGG(BINARY_CHECKSUM(*)) AS Fingerprint FROM dbo.Course;

   -- 3. Compatibility level, read or write, and the performance kit's objects
   SELECT name, compatibility_level, CAST(DATABASEPROPERTYEX(name, 'Updateability') AS nvarchar(20)) AS Updateability FROM sys.databases WHERE name = DB_NAME();
   SELECT name FROM sys.objects WHERE name IN (N'usp_SearchStudents', N'usp_GetStudentEnrollments', N'vw_EnrollmentStatistics') ORDER BY name;
   ```

   The two connections must give the same answer for every query, except `Updateability`: `READ_WRITE` on the source and `READ_ONLY` on the replica. The compatibility level is `110` on both, and the last query lists three objects on both. If a count differs, wait a minute (the replica catches up) and run it again. If it still differs, or something else looks wrong, abort and reseed: don't cut over on a replica you haven't checked.

   Done when the row counts, both fingerprints, the compatibility level and the three objects match on both connections.
4. **Stop every writer to the source, then cut over.** <span class="sl-badge note">vm-dev01</span> <span class="sl-badge caution">vm-app01</span> <span class="sl-badge tip">Azure portal</span> The source stays writable even after cutover, so any write after your final lag reading is lost. Tell your coach you're about to stop the writers and wait for their go-ahead. Then do these steps in order.

   **Don't script the cutover.** Use the **Monitor and cutover** pane, not a command: `az sql mi link failover` run from the managed instance's side fails, because the managed instance is the secondary at that point, and failing over by hand on SQL Server skips the portal's checks. [The guide](../../guides/arc-mi-link/#why-the-cutover-isnt-scripted) has the detail; don't run those commands.

   1. <span class="sl-badge note">vm-dev01</span> **Stop anything on `vm-dev01` that writes to the source.** Close the SSMS windows connected to `10.10.<n>.4`. Close the modernized app if you left it running from C6 (stop `dotnet run`, or the debug session, and close its terminal), and don't run `Reset-PerfKit.ps1`. `Start-Workload.ps1` only reads, but stop it too. Don't stop the VM itself.
   2. <span class="sl-badge caution">vm-app01 · Admin PowerShell</span> **Stop the legacy app on `vm-app01`.** Connect through Bastion, open an Administrator Windows PowerShell, and stop the site and its application pool (IIS runs the site, and the pool is what keeps database connections open). Leave SQL Server running: the link needs it.

      ```powershell title="vm-app01 — Administrator Windows PowerShell"
      Import-Module WebAdministration
      Stop-Website -Name ContosoUniversity
      Stop-WebAppPool -Name ContosoUniversity
      (Get-Website -Name ContosoUniversity).State
      (Get-WebAppPoolState -Name ContosoUniversity).Value
      ```

      Both lines must print `Stopped`. From `vm-dev01`, `http://10.10.<n>.4/` must no longer load.
   3. <span class="sl-badge caution">vm-app01 · Admin PowerShell</span> **Check nothing else is connected to the database.** Still on `vm-app01`, in the same PowerShell:

      ```powershell title="vm-app01 — Administrator Windows PowerShell"
      $query = "SELECT session_id, login_name, host_name, program_name, status FROM sys.dm_exec_sessions WHERE is_user_process = 1 AND database_id = DB_ID('ContosoUniversity') AND session_id <> @@SPID"
      $conn = New-Object System.Data.SqlClient.SqlConnection 'Server=localhost;Database=master;Integrated Security=True;TrustServerCertificate=True'
      $conn.Open()
      $cmd = $conn.CreateCommand()
      $cmd.CommandText = $query
      $table = New-Object System.Data.DataTable
      $table.Load($cmd.ExecuteReader())
      $conn.Close()
      $table | Format-Table
      "Sessions: $($table.Rows.Count)"
      ```

      An empty table and `Sessions: 0` is what you want. A row means a client is still connected: use `host_name` and `program_name` to find it (an SSMS window on `vm-dev01` is the usual one), close it, and run the check again.
   4. <span class="sl-badge tip">Azure portal</span> **Watch the lag reach zero.** Open the **Monitor and cutover** pane (**Database migration** > **Monitor migrations**). With no writers, the status of `ContosoUniversity` stays **Ready for cutover** and the **Lag** column shows two dashes, which means no lag, within a minute or two. If lag doesn't clear, or a writer keeps appearing, **postpone the cutover**: restart the site and pool (`Start-WebAppPool -Name ContosoUniversity; Start-Website -Name ContosoUniversity`), keep the link running, and agree a later window with your coach.
   5. <span class="sl-badge tip">Azure portal</span> **Cut over at no lag.**

      :::caution[Go/no-go: confirm with your coach before selecting Cutover]
      **Go only when** the replica checks from requirement 3 match, the source writers are stopped, the session check shows `Sessions: 0`, and the portal shows **Ready for cutover** with two dashes in **Lag** (no lag). Wait for the coach's go decision.

      **On a no-go:** Restart the legacy site and pool, keep the link running, and agree on a later window with your coach.
      :::

      Select `ContosoUniversity`, then **Cutover**. Microsoft Learn uses this label, but some portal builds show **Complete cutover** for the same action. Tick the box that confirms you've stopped all incoming traffic to the source, and leave the **forced failover** box clear: a planned failover waits for the lag to reach zero, and forcing it with lag above zero can lose writes. The portal removes the link when the cutover completes: it offers no option to keep it.
   6. <span class="sl-badge tip">Azure portal</span> <span class="sl-badge note">vm-dev01 · SSMS</span> **Wait for it to finish.** It takes about 2 minutes. On **Monitor and cutover**, the migration for `ContosoUniversity` shows as completed and the link is gone. Then, in SSMS on `vm-dev01` on the replica connection from requirement 3, run `SELECT DATABASEPROPERTYEX('ContosoUniversity', 'Updateability');`. It must return `READ_WRITE` (it said `READ_ONLY` in requirement 3).

   Done when the migration shows completed and the managed instance's database returns `READ_WRITE`. The managed instance is now the live database. Leave the legacy site on `vm-app01` stopped: restarting it would write to a source that's no longer authoritative.
5. **Write the secret and create the database user.** <span class="sl-badge note">vm-dev01 · PowerShell 7</span> <span class="sl-badge note">vm-dev01 · SSMS</span> After cutover, follow the first two go-live actions in [Step 5 of the modernization playbook](https://github.com/jonathan-vella/apex-factory-hackathon/blob/main/.github/modernization/playbook.md#c7-go-live-after-cutover) (the single source for the commands and checks), as the archetype's deployer:
   - **Action 1** (<span class="sl-badge note">vm-dev01 · PowerShell 7</span>): write the `ConnectionStrings--DefaultConnection` secret to `kv-university-$suffix`.
   - **Action 2** (<span class="sl-badge note">vm-dev01 · SSMS</span>): on the `ContosoUniversity` database on `$mi`, run `CREATE USER [id-university-<suffix>] FROM EXTERNAL PROVIDER` and grant the three database roles.
6. **Point the web app at your latest verified C6 image** and restart it. <span class="sl-badge note">vm-dev01 · PowerShell 7</span> <span class="sl-badge tip">Browser</span> Run **Action 3** in [Step 5 of the modernization playbook](https://github.com/jonathan-vella/apex-factory-hackathon/blob/main/.github/modernization/playbook.md#c7-go-live-after-cutover) in PowerShell 7 on `vm-dev01`. Set `$tag` to the tag you actually published and checked, including any later gap-fix build; do not deploy an older `c6` image over it. The web app pulls from your private registry with its managed identity.

   Done when `https://app-university-<suffix>.azurewebsites.net/` returns HTTP 200 and loads the home page in your browser (full functional and acceptance checks run in C8).
7. **Follow up on C3's trace-flag decision:** remove `-T1800` and `-T9567` from the source now that the link is gone. <span class="sl-badge caution">vm-app01 · Admin PowerShell</span>

   In your Administrator Windows PowerShell session on `vm-app01`, run `Prepare-MiLinkSource.ps1 -RemoveTraceFlags`:

   ```powershell title="vm-app01 — Administrator Windows PowerShell"
   C:\LabTools\Prepare-MiLinkSource.ps1 -RemoveTraceFlags
   ```

   The script verifies no distributed availability group (MI link) is active, removes only `-T1800` and `-T9567` from the SQL Server startup parameters in the registry while preserving all other startup flags, restarts `MSSQLSERVER`, and verifies with `DBCC TRACESTATUS(-1)` that neither trace flag is on. Done when it prints `Restarted MSSQLSERVER and verified with DBCC TRACESTATUS(-1) that trace flags 1800 and 9567 are off.`
8. **Update the concise cutover runbook.** <span class="sl-badge note">vm-dev01 · C:\src\\&lt;your-repo&gt;</span> Open the pre-created `factory/evidence/c07/cutover-rollback-runbook.md` in `C:\src\<your-repo>` on `vm-dev01`, tick the pre-cutover checklist, record your brief cutover summary and customer recovery notes, and commit and push on `main`:

   ```powershell title="vm-dev01 — C:\src\<your-repo> (pwsh)"
   cd C:\src\<your-repo>
   git pull --rebase
   git add factory/evidence/c07/cutover-rollback-runbook.md
   git commit -m "docs: C7 cutover and rollback runbook"
   git push
   ```

   **Rollback scope:** the event exercises a pre-cutover abort/reseed, not rollback after cutover. Document the pre-cutover abort path and name the customer procedure needed afterward: backup restore or planned `failback`, with data reconciliation and an agreed recovery window. Never restart the stale source as a shortcut after the managed instance has accepted writes.

<details>
<summary>If link creation fails</summary>

Work through these in order:

1. Requirement 1 must have finished with `The source is ready for MI link.` Read `C:\LabTools\logs\Prepare-MiLinkSource.log` on `vm-app01`. An `ERROR:` line that says the instance is not ready means a datacenter setting is missing: tell your coach.
2. The prefix you passed must be your own `10.20.<n>.128/26` (or the exact `-MiSubnetPrefix` printed by the dev-container command when `<n>` is `256` or higher). A wrong prefix opens port 5022 to the wrong subnet and the link can't connect. Run the script again with the right one: it fixes the firewall rule.
3. `vm-app01` must be running with its Arc entry **Connected**, and the SQL Server service must be running.
4. **Test connection** can pass while creation still fails, so read the error the portal shows on **Monitor migrations** and send it to your coach. Don't change firewall, network or certificate settings by hand.
5. To retry, select **Cancel migration**, delete the leftover copy on the managed instance (the next hint), and start again from requirement 2. Requirement 1 doesn't need repeating.

</details>

<details id="abort-leftover">
<summary>The abort leaves something behind</summary>

In the Azure portal, **Monitor and cutover** > select the database > **Cancel migration** removes the link without a failover. An aborted link leaves a writable copy of the database on the MI, and the source is untouched (restart the legacy site if you stopped it). Delete the copy before starting a new seed, or the reseed fails. This deletes the copy on the managed instance only; the database on `vm-app01` isn't affected. On `vm-dev01`:

```powershell title="vm-dev01 — PowerShell 7"
az sql midb delete --resource-group $rg --managed-instance "sqlmi-university-$suffix" --name ContosoUniversity --yes
```

Then start the link again from requirement 2.
</details>

<details>
<summary>CREATE USER fails</summary>

Before cutover, the replica is read-only, so the user creation step only works after cutover completes (requirement 4, step 6). If it still fails afterward with a permissions error on the server's Entra identity, ask your coach: the MI's primary identity needs Microsoft Graph read access, set up at Step 2.2 and checked at Day 2 08:30 above. C2 requirement 3 checks connectivity, not the Graph grant.
</details>

<details>
<summary>The app won't start against App Service</summary>

Check the Key Vault secret exists and has the right name (`ConnectionStrings--DefaultConnection`, with the double dash), and that the database user was created with the identity's exact name.
</details>

<details>
<summary>If you need to start over</summary>

Before the cutover, cancel and reseed: **Cancel migration** in the portal, delete the copy on the managed instance (see the hint "The abort leaves something behind"), then start again from requirement 2. After the cutover there's no link to remove: the managed instance is the live database, so ask your coach before you change anything. If the web app won't start after go-live, check the Key Vault secret and the database user first, then ask your coach.

</details>
