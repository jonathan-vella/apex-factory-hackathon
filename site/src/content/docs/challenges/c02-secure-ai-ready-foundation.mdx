## Goal

Verify and explain the landing zone that already exists. The platform lead deployed ALZ-lite before the event and vended every member into it. On day one you watch a live portal ALZ demo, walk through what ALZ-lite built and why, check the Graph grant, your own exemptions and your own connectivity, and answer the coach's questions on the policies.

## Scope and time box

Team. **120 min**. Nothing deploys during C2: the platform lead deployed ALZ-lite at T-7 and vended every member at T-1 (see "Before the event" below). The coach's demo (task 2) opens C2 at 09:45. The platform lead leads the walk-through (tasks 3 to 5) with the team; every member does tasks 1, 6 and 7 for their own datacenter.

**How C2 fits around C3.** Members start C3 at 10:15. Do tasks 6 and 7 (about 15 minutes) at a clean point in C3, for example right after the `app: assess and plan` commit, then go back to C3. Your subscription was vended at T-1, so your `vm-dev01` already uses the hub's DNS and routes and nothing needs a restart. **Restart a VM only when a probe fails for DNS and no agent run is in progress on `vm-dev01`:** a restart ends your Bastion session and the run in it.

## Points

**35 pts** (team).

## Inputs

C1's opportunity canvas (context only — C2 doesn't depend on its content), and the foundation built before the event.

## Before the event

The platform lead does this work, with a Privileged Role Administrator for one step. Two pipeline stages build the foundation, and a coach reviews C0 between them. This is what C2's evidence comes from, so keep the run summary of every stage. The pipeline redacts IDs: they show as `<id:abcd>`. Still, don't put subscription, tenant or object IDs in anything you commit.

The order is fixed by the dependencies. ALZ-lite comes before vending, because vending finds the hub by name. Each member's datacenter comes before vending, because vending connects it, and the `member` stage tests the datacenter before Arc onboarding (C0). The Graph grant comes after ALZ-lite, because ALZ-lite creates the identity it grants, and before C7. Vending comes after each member's `vm-dev01` setup and the coach's C0 review on purpose: vending changes the datacenter's DNS servers to the hub firewall, and `vm-dev01` setup doesn't test that.

| When | Who | What |
|---|---|---|
| T-14 | Event owner | Captures every member's workload subscription ID, member index, Entra object ID and email in the private roster. Members run the preflight |
| T-7 | Platform lead, then a Privileged Role Administrator | Runs the `foundation` stage (ALZ-lite), then the Graph grant |
| T-3 | Each member | Does C0 in their own repo; a coach reviews every member's output |
| T-1 | Platform lead | Runs the `vending` stage: it vends every member in order, restarts the VMs, records the exemptions and runs the connectivity probes |

**T-7: ALZ-lite and the Graph grant.** In the platform lead's dev container, from `factory/`, run the `whatif` stage first (a read-only what-if, plus the preflight for every member), then the `foundation` stage. [Deploy with GitHub Actions](../../guides/deploy-with-actions/#platform-lead) has the setup and the roster.

```bash
gh workflow run platform.yml -f stage=whatif
gh workflow run platform.yml -f stage=foundation
```

The foundation deploys unattended in about 15 to 25 minutes, mostly Azure Firewall. It creates the management groups, the hub (Azure Firewall Standard with DNS proxy, central private DNS zones), the central Log Analytics workspace, and the core policies at `mg-factory-corp`. It creates the identity `id-sqlmi-directory` in `rg-management`, which the grant needs. It's done when the run is green and its summary says ALZ-lite is deployed. The firewall bills about $1.30 an hour from now until the event is cleaned up.

Right after it, the Privileged Role Administrator grants the SQL MI identity its Graph read, once per team. Every member's SQL Managed Instance uses `id-sqlmi-directory`, and without this grant C7 can't create the web app's database user (`CREATE USER ... FROM EXTERNAL PROVIDER` fails with "Server identity does not have Azure Active Directory Readers permission"). Only someone with the Privileged Role Administrator (or Global Administrator) Microsoft Entra directory role can grant it, and the platform lead usually doesn't hold that role, so the event owner books that person for T-7. They run the two commands below from their own computer, in the kit's `factory/` folder, signed in as themselves with `az login`. Don't have them sign in inside the platform lead's dev container: a second `az login` there replaces the lead's. Give them the shared services subscription ID. They don't need your repo: the script is one file with no other kit dependencies, so they download [`Grant-SqlMiDirectoryRead.ps1`](https://raw.githubusercontent.com/jonathan-vella/apex-factory-hackathon/main/scripts/Grant-SqlMiDirectoryRead.ps1), install PowerShell 7 and the Azure CLI, and run it from the folder that holds the file (use `./Grant-SqlMiDirectoryRead.ps1` instead of `./scripts/...`).

```powershell
./scripts/Grant-SqlMiDirectoryRead.ps1 -SharedSubscriptionId '<shared-services-subscription-id>' -WhatIf
./scripts/Grant-SqlMiDirectoryRead.ps1 -SharedSubscriptionId '<shared-services-subscription-id>'
```

It's done when the second run reports the three Graph permissions (`User.Read.All`, `GroupMember.Read.All`, `Application.Read.All`) as granted. A re-run skips what is already granted. Ask the role holder to share the output with you for your evidence. If the identity lookup is denied, give that person Reader on the shared services subscription first.

**T-1: vending.** Start both VMs of every member first if they were stopped, and only vend a member whose datacenter exists and whose C0 a coach has reviewed. The platform lead is also a student with one workload subscription: vend yourself too. The roster file holds the four values the event owner captured at T-14 for each member (workload subscription ID, member index, Entra object ID and email), so nobody types them and nobody commits them to any repo. The location is the team's, the same for everyone.

Run the stage once. Without `members` it vends every member in the roster, one after another (each run updates the same firewall policy):

```bash
gh workflow run platform.yml -f stage=vending
```

Each member is connected to the hub: spoke, subnets, peering, UDRs, DNS, firewall rules, RBAC and a budget, in 4 to 5 minutes per member. The member's Owner role, their Reader role on the shared services subscription (which `Test-Connectivity.ps1` and C5's preflight need to read the hub) and the Managed Identity Operator grant on `id-sqlmi-directory` come from the roster's Entra object ID. If a member already holds a direct Owner assignment, vending keeps it. After each member, post "vended" with the member's name in the team channel. It's done when the run is green.

Vending changes each datacenter's DNS servers and routes, and running VMs keep their old settings. So the stage restarts both VMs of every member (tell the member first: a restart ends their Bastion session), records the policy exemptions, then runs the connectivity probes. Each exemption needs an owner, a reason and an expiry (the default is 14 days), and the stage records `GitHub Actions pipeline` as the owner. Policy changes can take up to 30 minutes to take effect after ALZ-lite, so if a member's exemptions come back empty, wait and run `gh workflow run platform.yml -f stage=vending -f members=<member-index>` for that member only. The probes are done when every applicable check is PASS.

Copy the run summaries of the `foundation` and `vending` stages as your team's evidence (see Evidence below).

## What the foundation holds

The highlighted parts are what the platform lead put in place before the event, and what C2 verifies: the management groups, the hub with its firewall, private DNS zones and workspace, and for each member the spoke, the peering and the routes. Your datacenter is there from C0.

<ArchitectureDiagram highlight="c2" name="c2-arch" caption="Highlighted: the foundation C2 verifies, built before the event. n is your member index." />

Terms on this page:

- **Management group:** a container above subscriptions. Policy and access set on it apply to everything under it.
- **Hub and spoke:** the hub is the shared virtual network (`vnet-hub`) with the firewall and the central private DNS zones. Each member's spoke (`vnet-spoke`) connects to it through a peering.
- **Firewall DNS proxy:** Azure Firewall answers the VMs' DNS queries, so they resolve the private names of Azure services.
- **UDR:** a user-defined route. Here, a route that sends the spoke's traffic through the hub firewall.
- **Vending:** connecting a member's workload subscription and datacenter to the hub.
- **Exemption:** a recorded, time-limited exception to a policy for one resource, with an owner, a reason and an expiry.
- **Graph read:** Microsoft Graph read permissions that let SQL Managed Instance look up Microsoft Entra users and apps.

## Your tasks

1. **Members: record the shared services subscription ID.** The platform lead posted it in the team channel when they vended you; ask if you can't find it. (Platform lead: skip this task, your settings already hold the ID from Prerequisites.) In the terminal above, add it to your settings, then reload `$s`. The script asks nothing; it prints the path of your settings file and your suffix.

   ```powershell
   ./scripts/Initialize-Settings.ps1 -SharedSubscriptionId '<shared-services-subscription-id>'
   $s = Get-Content .local/settings.json | ConvertFrom-Json
   $s.sharedSubscriptionId
   ```

   Done when the last line prints the shared services subscription ID the platform lead gave you.
2. Watch the coach's live demo of a full portal-based Azure Landing Zone, and note what ALZ-lite deliberately leaves out (it's a comparison table in the [ALZ-lite guide](../../guides/alz-lite/), not a gap to fix). Done when you can name two things a full ALZ has that ALZ-lite leaves out.
3. **Platform lead, with the team: walk through ALZ-lite and answer the coach's questions.** Using the T-7 `foundation` run summary and the portal, show the team what the foundation holds: the management groups (`mg-factory`, with `mg-factory-platform` and `mg-factory-corp` beneath it), `rg-hub` (`vnet-hub`, `afw-hub`, `afwp-hub`, the central private DNS zones), `rg-management` (`log-management` and `id-sqlmi-directory`) and the `ALZ-lite:` policy assignments at `mg-factory-corp` (**Policy** > **Assignments**, with the scope set to `mg-factory-corp`). The coach then asks about the core policies, for example: which assignments only audit, which deny, and which add a missing setting? What would the Deny on public network access stop in C5? Why does the firewall act as DNS proxy? The [ALZ-lite guide](../../guides/alz-lite/) has the summary table. Done when the team can say, for each kind of core policy, what its effect does to a resource, and the platform lead has shown the T-7 run summary.
4. **Platform lead: show the Graph grant is in place.** The Privileged Role Administrator made the grant at T-7. Check it now, in your own dev container, from `factory/`. It changes nothing:

   ```powershell
   ./scripts/Grant-SqlMiDirectoryRead.ps1 -SharedSubscriptionId $s.sharedSubscriptionId -WhatIf
   ```

   Done when the output says each of the three Graph permissions (`User.Read.All`, `GroupMember.Read.All`, `Application.Read.All`) is already granted, and you can explain in one sentence why C7 needs it. If it isn't granted, ask your coach to bring the Privileged Role Administrator back: C7 can't create the web app's database user without it, and the steps are under "Before the event".
5. **Platform lead, with the team: explain what vending did.** Show the T-1 `vending` run summary for every member (IDs are already redacted), and for one member the spoke in the portal: `rg-spoke`, `vnet-spoke` with `snet-app`, `snet-pe` and `snet-sqlmi`, the peering to the hub, the route table that sends traffic to the firewall, the DNS servers set to the hub firewall, the budget and the RBAC. The coach asks the members to explain why vending came after their datacenter existed (the exemptions in task 6 depend on it) and why it came after `vm-dev01` setup (it changes the datacenter's DNS to the firewall). Done when the run summary covers every member of the team, and each member has seen their own spoke.
6. **Every member (including the platform lead): check and explain your datacenter's exemptions.** The datacenter was deployed before your subscription moved under `mg-factory-corp`, so the landing zone's policies flag it. Vending at T-1 recorded exemptions for it. Check that the `ALZ-lite:` policy assignments are visible on your subscription (they're inherited from `mg-factory-corp`), then list your exemptions:

   ```powershell
   az account set --subscription $s.subscriptionId
   az policy assignment list --disable-scope-strict-match -o table
   az policy exemption list --resource-group rg-datacenter --query "[].{name:displayName, category:exemptionCategory, expires:expiresOn, description:description}" -o table
   ```

   Each exemption needs an owner, a reason and an expiry in its description and expiry columns. If the list is empty, the policies hadn't taken effect when vending ran (policy changes can take up to 30 minutes after ALZ-lite): ask the platform lead to run `gh workflow run platform.yml -f stage=vending -f members=<your-member-index>` again, then list again. The owner is `GitHub Actions pipeline`, because the stage records them. Explain to the coach why the datacenter gets an exemption and not a fix, and who owns the deferred work when each exemption expires. Done when you have the exemptions table, with owner, reason and expiry for each row, saved: you carry its rows into the deferred-work register in C4.
7. **Every member: re-run the connectivity probes (about 10 min).** The platform lead ran them at T-1, and you now run them yourself. It's read-only: it runs its checks inside your datacenter VMs through Azure, so you don't sign in to the VMs. Run this from your own dev container, from `factory/`:

   ```powershell
   ./scripts/Test-Connectivity.ps1 -SubscriptionId $s.subscriptionId -SharedSubscriptionId $s.sharedSubscriptionId -MemberIndex $s.memberIndex
   ```

   Done when every applicable check is PASS. If one fails, see the hint "DNS stops resolving for a running VM after vending".

## Hints

<details>
<summary>Vending fails to find the hub</summary>

The `vending` stage discovers the hub by the ALZ-lite naming convention (`vnet-hub`, `afw-hub`, `afwp-hub`, `rg-hub`) in the shared services subscription. Confirm the `foundation` stage finished and those names exist before running vending.
</details>

<details>
<summary>Policy evaluation shows the datacenter as non-compliant</summary>

That's expected until exemptions exist — the datacenter was deployed before the workload subscription moved under `mg-factory-corp`. Record it as deferred work, don't fight the policy.
</details>

<details>
<summary>DNS stops resolving for a running VM after vending</summary>

VNet DNS servers changed, but running VMs keep their old settings. The platform lead restarts both VMs at T-1; if yours were stopped or redeployed since, restart them (`az vm restart -g rg-datacenter -n vm-dev01 --subscription $s.subscriptionId`, then `-n vm-app01`), only when no agent run is in progress on `vm-dev01`, then run `Test-Connectivity.ps1` again. Your Bastion session drops: reconnect through Bastion and open VS Code on `C:\src\factory`.
</details>

## If you need to start over

Run the `foundation` and `vending` stages again: both converge on existing resources. If a member's datacenter is redeployed (C0), the platform lead runs the `vending` stage for that member again (`-f members=<n>`): it restarts both of their VMs and records their policy exemptions again. ALZ-lite bills about $1.30 an hour while it exists, because of the firewall. After the event the platform lead runs the `teardown` stage, which removes every member first, then the team's foundation. Deleting `rg-hub` alone stops the firewall cost but leaves the peering to each spoke, the policy assignments, the management groups and the budgets behind.

## Bonus

Up to 5 pts for running the negative tests from the foundation's validation record (`factory/infra/foundation/validation.md`, section "Negative tests") yourself and recording the results: a container registry with public network access denied, a NIC with a public IP denied, and a private endpoint without a DNS zone group getting one added in the central DNS zone (this can take about 12 minutes). The private endpoint test needs a target resource, such as a test storage account, so create and delete it yourself. Record the actual denial messages, not just "it worked", and delete everything you create.
