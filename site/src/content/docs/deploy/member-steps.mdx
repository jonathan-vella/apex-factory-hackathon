**Path:** **Path A: Self-service teams** (in a lead-provisioned cohort, the team lead deploys the datacenters and attendees follow [Student onboarding](/deploy/lead-setup/student-onboarding/)).
**Who:** **Everyone** (every member, including the team lead).
**When:** By **T-3** (3 days before day one). About 35 to 60 minutes unattended for the `member` stage, plus 30 minutes to set up `vm-dev01`.

Complete [Step 1: Repo and preflight (T-14)](../set-up-your-repo/) first. Run the Step 3.1–3.2 commands from `~/src/<your-repo>/factory` in PowerShell (`pwsh`) inside [Azure Cloud Shell](https://shell.azure.com). Once `vm-dev01` is deployed, you set up `C:\src\<your-repo>` on `vm-dev01` in Step 3.3 and work there for the rest of the event. Your **designated team lead** is your first point of contact if you hit a problem.

The datacenter starts billing when you deploy it in Step 3 and continues until teardown at T+2, including while its VMs are deallocated. See [Cost](../../reference/cost/) for per-member rates and event estimates.

Check that you are signed in and load your settings in each new terminal:

```powershell
az account show --output table
$s = Get-Content .local/settings.json | ConvertFrom-Json
az account set --subscription $s.subscriptionId
```

If `az account show` fails, sign in again with `az login --use-device-code`. `$s` holds `subscriptionId`, `memberIndex`, `suffix` and `location`.

## 3.1 Deploy your datacenter and onboard Azure Arc

<Diagram
  name="diagram-05-simulated-datacenter"
  alt="Your datacenter in your own workload subscription: vm-app01 runs the legacy Contoso University on IIS with SQL Server 2022 and is Arc-enabled; vm-dev01 is your Windows 11 workstation with VS Code, GitHub Copilot and the Upgrade agent. Both have no public IP and are reached through Azure Bastion, with a NAT gateway for outbound traffic."
  caption="What the member stage builds: vm-app01 (the legacy app) and vm-dev01 (your workstation), reached through Bastion."
/>

The `member` stage runs preflight (`Test-Preflight.ps1 -Fix`), deploys `rg-datacenter` with `vm-app01` (legacy Contoso University on IIS, SQL Server 2022, MSMQ) and `vm-dev01` (your Windows 11 workstation), runs `Test-Datacenter.ps1` while both VMs are running, and—only if every check passes—connects `vm-app01` to Azure Arc.

:::note[Pick the command for your role (never run both)]
In Path A, everyone—including the team lead—deploys their own datacenter at **T-3**. Because the team lead's repository holds the team-wide `Lead` pipeline (`roster.json` for slots `1..n`), GitHub Actions requires `-f members=1` there so the lead deploys **only their own slot `1` datacenter** instead of every teammate's subscription. Every other member's repository holds a single-user `Member` pipeline, so no `-f members=...` flag is needed.
:::

<Steps>

1. **Deploy your datacenter (`T-3`, in Azure Cloud Shell — `~/src/<your-repo>/factory`).** Run **one** command matching your role:
   - **If you are a team member (indexes `2..n`):**

     ```bash
     gh workflow run platform.yml -f stage=member
     ```

   - **If you are the team lead (deploying your own slot `1` datacenter):**

     ```bash
     gh workflow run platform.yml -f stage=member -f members=1
     ```

   Open the **Actions** tab on GitHub and approve the run if prompted. *(No Windows Server Azure Hybrid Benefit licenses? Append `-f no-hybrid-benefit=true` to this first dispatch and tell your team lead; see [Azure Hybrid Benefit](../../reference/azure-hybrid-benefit/).)*

2. **Check the test result in the Actions run summary.** `Test-Datacenter.ps1` checks VM state and size, license type, Trusted Launch (secure boot and vTPM), no public IPs, Azure Bastion Standard, and in-VM checks (IIS up, SQL Server up, and the performance kit's planted data present). It runs before Arc because Arc turns off the VM run commands that the in-VM checks use. Done when every row is PASS.

3. **Confirm Azure Arc.** In the Azure portal, open **Azure Arc** > **Machines**. Done when `vm-app01` shows as **Connected** and **SQL Server instances** lists its SQL Server instance. The `vending` stage in Step 4 checks `vm-app01`'s Arc connection automatically before vending your spoke.

   Onboarding this Azure VM to Arc is a **lab-only simulation**. In a customer environment, onboard the on-premises servers instead.

</Steps>

If a run fails before Arc onboarding starts, read the run log, fix the cause, and run the same command again. After Arc starts, see [If you need to start over](#if-you-need-to-start-over).

## 3.2 Run the first Arc SQL assessment and check Hybrid Benefit

<Steps>

1. **Run the first Arc SQL migration assessment** (about 15 minutes). In **Azure Arc** > **SQL Server instances**, select the instance on `vm-app01`, then **Migration** > **Assessments**. Choose **Run assessment** if needed, open the readiness details and select **Azure SQL Managed Instance** as the target to review. Export the report or screenshot its findings for `ContosoUniversity`; you triage them in C3. This follows [Learn's assessment instructions](https://learn.microsoft.com/sql/sql-server/azure-arc/migration-assessment), checked **2026-10-30**, not a new portal test. Older portal versions use **Database migration** > **Assess source instance** > **View report**. The event owner revalidates the UI before the event.

2. **Confirm Azure Hybrid Benefit and VM power state** (about 5 minutes):

   ```powershell
   az vm list -g rg-datacenter -d -o table
   az vm show -g rg-datacenter -n vm-app01 --query licenseType -o tsv
   ```

   Done when both VMs are running and the second command prints `Windows_Server` (or `None` if you used `no-hybrid-benefit=true`).

</Steps>

## 3.3 Set up vm-dev01

<VmDev01Setup pathMode="self-service" />

### Check your setup

Run in **PowerShell 7 (`pwsh`)** on `vm-dev01`:

```powershell
gh auth status
git config --global user.name
az account show --query name -o tsv
[Environment]::GetEnvironmentVariable('AZURE_TOKEN_CREDENTIALS', 'User')
git -C C:\src\<your-repo> branch --show-current
git -C C:\src\<your-repo> status --short --ignored -- app .github/upgrades
Get-Content C:\src\<your-repo>\factory\.local\settings.json
```

Done when GitHub is signed in, git has your name, Azure shows your workload subscription, the variable is `AzureCliCredential`, `C:\src\<your-repo>` is on `main`, `settings.json` has your `suffix` and `memberIndex`, and the `git status` command prints nothing. VS Code must be open on `C:\src\<your-repo>`, with **Upgrade**, **Local** and a Copilot reply to "hello".

If the `git status` command lists leftovers under `app` or `.github/upgrades`, inspect them before removing files that git does not track:

```powershell
cd C:\src\<your-repo>
git clean -ndx -- app .github/upgrades
git clean -fdx -- app .github/upgrades
```

### Coming back later

[Reconnect to `vm-dev01` through Bastion](../../guides/connect-to-vms/#reconnect-later), using native RDP on Windows or the browser fallback, then open PowerShell 7 and run `code C:\src\<your-repo>`; do not repeat the clone. Read this site in the VM's browser or on your own computer. All challenge work and working artifacts live in `C:\src\<your-repo>` on `main`. Restart only when no agent run is active: a restart ends Bastion and interrupts the run. Never stop or deallocate `vm-dev01` during the event.

## 3.4 Confirm your readiness checklist

### Readiness checklist

Confirm that `factory/evidence/readiness/` in `C:\src\<your-repo>` on `main` holds `test-datacenter.txt` (committed in Step 3.3 step 1) and that these readiness checks are complete before Step 4 (T-1):

1. **Preflight GO.** The `whatif` **run log**, in the member's **Preflight** step, showing `GO`. WARN rows do not prevent GO; confirm the separate manual checks too.
2. **Datacenter test PASS before Arc.** `factory/evidence/readiness/test-datacenter.txt` committed on `main` with every check PASS.
3. **Arc connected, with the SQL extension.** `vm-app01` showing as **Connected** under **Azure Arc** > **Machines**, and its instance listed under **SQL Server instances** (checked automatically by Step 4 Vending).
4. **Arc migration assessment ready.** Assessment for `ContosoUniversity` against **Azure SQL Managed Instance** visible in the portal ready for C3 triage.
5. **Hybrid Benefit and VM state confirmed.** Both VMs running and `vm-app01`'s `licenseType` verified.
6. **`vm-dev01` and Copilot working.** `C:\src\<your-repo>` cloned on `main`, `factory/.local/settings.json` written, and Copilot Chat answering `"hello"` in VS Code on `vm-dev01`.

Let your team lead know as soon as your Step 3 checklist is complete so they know you are ready for [Step 4: Vending (T-1)](../vending/).

## Hints

For deployment, Arc or DNS errors, check [Troubleshooting](../../reference/troubleshooting/).

<details>
<summary>Arc onboarding doesn't finish</summary>

Arc onboarding needs outbound internet through the NAT gateway. Don't rerun `member` after onboarding starts: the stage refuses once `vm-app01` exists as an Arc machine. If onboarding stopped earlier but disabled its guest agent, a rerun instead fails at the datacenter test; that is not a safe repair path. Read the run log, connect through Bastion as in [Switching to vm-dev01](../../guides/ghcp-upgrade/#switching-to-vm-dev01) (use `vm-app01`, same password), and open `C:\LabTools\logs\Connect-AppArc.log` in Notepad.

Check with your team lead first, or follow [If you need to start over](#if-you-need-to-start-over).

</details>

<details>
<summary>Save money between sessions</summary>

Before the event you can stop both VMs when you're not working: `az vm deallocate -g rg-datacenter -n vm-app01`, then the same with `-n vm-dev01`. Running `az vm deallocate` releases the VM's compute and stops its compute billing. Shutting Windows down from inside the VM does not. Bastion, the NAT gateway and the disks bill even when the VMs are stopped.

Start both again before your team lead runs Step 4 at T-1 (`az vm start -g rg-datacenter -n vm-app01`, then `-n vm-dev01`), because vending restarts them and runs the connectivity probes inside them. During the event, never stop `vm-dev01`: it's your workstation.

</details>

## If you need to start over

- **Before Arc onboarding starts:** fix the error and re-run your Step 3.1 `member` command (`gh workflow run platform.yml -f stage=member` for a team member, or `gh workflow run platform.yml -f stage=member -f members=1` for the team lead).
- **After Arc onboarding starts, before C5:** `member` refuses an existing Arc machine, and a half-onboarded VM has guest run commands disabled. With the event owner's approval, tear down **only your member scope**, **wait for `teardown` to finish green in Actions**, and then re-run `member`:
  - **If you are a team member (indexes `2..n`, in your own repo):**

    ```bash
    gh workflow run platform.yml -f stage=teardown
    ```

    Once `teardown` finishes green:

    ```bash
    gh workflow run platform.yml -f stage=member
    ```

  - **If you are the team lead (recovering your own slot `1`—or helping recover one teammate's `<index>`—from your lead repo):** always pass `-f members=<index>` so you never tear down the rest of the team:

    ```bash
    gh workflow run platform.yml -f stage=teardown -f members=1
    ```

    Once `teardown` finishes green:

    ```bash
    gh workflow run platform.yml -f stage=member -f members=1
    ```

  Member cleanup removes `rg-datacenter`, `rg-spoke` and the archetype (including SQL Managed Instance). Repeat Step 3 and the `vm-dev01` setup afterward. Append `-f no-hybrid-benefit=true` to `member` if you lack eligible Windows Server licenses, and if your subscription was already vended in Step 4, have the team lead re-run `gh workflow run platform.yml -f stage=vending -f members=<index>` afterward.

:::caution
After C5, do not use this recovery; member teardown removes the archetype, including the SQL Managed Instance, which takes hours to provision again. Ask the event owner for a coach repair.
:::
