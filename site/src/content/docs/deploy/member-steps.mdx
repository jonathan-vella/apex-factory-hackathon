**Who:** **Everyone** (every member, including the team lead).
**When:** By **T-3** (3 days before day one). About 35 to 60 minutes unattended for the `member` stage, plus 30 minutes to set up `vm-dev01`.

Complete [Step 1: Repo and preflight (T-14)](../set-up-your-repo/) first. Run every command from the `factory/` folder in PowerShell (`pwsh`) inside your dev container. Your **designated team lead** is your first point of contact if you hit a problem.

The datacenter starts billing when you deploy it in Step 3 and continues until teardown at T+2, including while its VMs are deallocated. See [Cost](../../reference/cost/) for per-member rates and event estimates.

Check that you are signed in and load your settings in each new terminal:

```powershell
az account show --output table
$s = Get-Content .local/settings.json | ConvertFrom-Json
az account set --subscription $s.subscriptionId
```

If `az account show` fails, sign in again with `az login --use-device-code`. `$s` holds `subscriptionId`, `memberIndex`, `suffix` and `location`.

## 3.1 Deploy your datacenter and onboard Azure Arc

<Diagram
  name="diagram-05-simulated-datacenter"
  alt="Your datacenter in your own workload subscription: vm-app01 runs the legacy Contoso University on IIS with SQL Server 2022 and is Arc-enabled; vm-dev01 is your Windows 11 workstation with VS Code, GitHub Copilot and the Upgrade agent. Both have no public IP and are reached through Azure Bastion, with a NAT gateway for outbound traffic."
  caption="What the member stage builds: vm-app01 (the legacy app) and vm-dev01 (your workstation), reached through Bastion."
/>

The `member` stage creates `rg-datacenter` with `vm-app01` (legacy Contoso University on IIS, SQL Server 2022, MSMQ) and `vm-dev01` (your Windows 11 workstation), runs `Test-Datacenter.ps1` while both VMs are running, and only if every check passes connects `vm-app01` to Azure Arc.

<Steps>

1. **Start the `whatif` and `member` stages.**
   - **In your own repo (member profile):**

     ```bash
     gh workflow run platform.yml -f stage=whatif
     gh workflow run platform.yml -f stage=member
     ```

   - **In the team lead's repo:** run `member` only for your index from `roster.json`:

     ```bash
     gh workflow run platform.yml -f stage=member -f members=<your index>
     ```

2. **Check the test result in the Actions run summary.** `Test-Datacenter.ps1` checks VM state and size, license type, Trusted Launch (secure boot and vTPM), no public IPs, Azure Bastion Standard, and in-VM checks (IIS up, SQL Server up, and the performance kit's planted data present). It runs before Arc because Arc turns off the VM run commands that the in-VM checks use. Done when every row is PASS.

3. **Confirm Azure Arc.** In the Azure portal, open **Azure Arc** > **Machines**. Done when `vm-app01` shows as **Connected** and **SQL Server instances** lists its SQL Server instance. The `vending` stage in Step 4 checks `vm-app01`'s Arc connection automatically before vending your spoke.

   Onboarding this Azure VM to Arc is a **lab-only simulation**. In a customer environment, onboard the on-premises servers instead.

</Steps>

If a run fails, read the run log. The `member` stage is safe to run again until Arc onboarding starts. After Arc starts, see [If you need to start over](#if-you-need-to-start-over).

**No Windows Server licenses?** Azure Hybrid Benefit is on by default for `vm-app01`. If you do not hold eligible licenses, set the input on the initial member stage and let your team lead know, as described on the [Azure Hybrid Benefit](../../reference/azure-hybrid-benefit/) page:

- In your own repo (member profile): `gh workflow run platform.yml -f stage=member -f no-hybrid-benefit=true`
- In the team lead's repo: `gh workflow run platform.yml -f stage=member -f members=<your index> -f no-hybrid-benefit=true`

## 3.2 Run the first Arc SQL assessment and check Hybrid Benefit

<Steps>

1. **Run the first Arc SQL migration assessment** (about 15 minutes). In **Azure Arc** > **SQL Server instances**, select the instance on `vm-app01`, then **Migration** > **Assessments**. Choose **Run assessment** if needed, open the readiness details and select **Azure SQL Managed Instance** as the target to review. Export the report or screenshot its findings for `ContosoUniversity`; you triage them in C3. This follows [Learn's assessment instructions](https://learn.microsoft.com/sql/sql-server/azure-arc/migration-assessment), checked **2026-10-30**, not a new portal test. Older portal versions use **Database migration** > **Assess source instance** > **View report**. The event owner revalidates the UI before the event.

2. **Confirm Azure Hybrid Benefit and VM power state** (about 5 minutes):

   ```powershell
   az vm list -g rg-datacenter -d -o table
   az vm show -g rg-datacenter -n vm-app01 --query licenseType -o tsv
   ```

   Done when both VMs are running and the second command prints `Windows_Server` (or `None` if you used `no-hybrid-benefit=true`).

</Steps>

## 3.3 Set up vm-dev01

From C3 onward you do the application and database modernization work on `vm-dev01`, so set it up completely now. First download your readiness evidence and lab credentials file (`datacenter.json`) from `factory/` in your dev container:

```powershell
./scripts/Get-PipelineEvidence.ps1
```

If Arc failed, the successful-run evidence download may not yet exist. Use the documented lab-password reference in [Datacenter credentials](https://github.com/jonathan-vella/apex-factory-hackathon/blob/main/infra/datacenter/README.md#credentials) for the standard disposable lab, or ask your team lead privately for a custom deployment's password. Do not publish it or rerun `member` merely to recreate the credentials file.

Use two browser windows on your own computer: one for Bastion, the other for the portal and this site. Allow portal pop-ups and Bastion clipboard access. Enter sign-in codes on your own computer, where your passkeys and password manager work.

Steps 1 and 2 below run on your own computer; steps 3 to 9 run on `vm-dev01`, in **PowerShell 7** (`pwsh`), not Windows PowerShell 5.1. `<your-org>` and `<your-repo>` are the owner and name of your own private repo.

1. **Get the password and subscription.** In PowerShell in your dev container, from `factory/`:

   ```powershell
   $s = Get-Content .local/settings.json | ConvertFrom-Json
   (Get-Content ".local/$($s.subscriptionId)/datacenter.json" | ConvertFrom-Json).adminPassword
   $s.subscriptionId
   git remote get-url origin
   ```

   The outputs are the password for `labadmin`, your workload subscription ID and your repo URL. Keep them privately for the next steps. The password also opens `vm-app01`. If the file is missing, run `./scripts/Get-PipelineEvidence.ps1` from `factory/` first.
2. **Connect through Bastion.** In the Azure portal, check your directory and workload subscription filter. Open **Resource groups** > **rg-datacenter** > **vm-dev01** > **Connect** > **Bastion**. Choose **Password**, enter `labadmin` and the password, then **Connect**. After your first sign-in, wait up to five minutes for the VS Code extensions to install. On a Windows computer, `./scripts/Connect-DatacenterVm.ps1` is an optional shortcut; it needs PowerShell 7, Azure CLI with the `bastion` extension and a local copy of `factory/`.
3. **Sign in to GitHub and set your git identity.** Open PowerShell 7 on the VM:

   ```powershell
   gh auth login --web
   gh auth setup-git
   $u = gh api user | ConvertFrom-Json
   git config --global user.name ($u.name ?? $u.login)
   git config --global user.email "$($u.id)+$($u.login)@users.noreply.github.com"
   ```

   Choose **GitHub.com**, **HTTPS** and **Yes** to authenticate Git. Enter the one-time code at `https://github.com/login/device` on your own computer. `gh auth setup-git` lets pushes use that sign-in.
4. **Sign in to Azure with your own identity.** Still on the VM:

   ```powershell
   az login --use-device-code
   az account set --subscription '<workload-subscription-id>'
   az account show --query name -o tsv
   [Environment]::SetEnvironmentVariable('AZURE_TOKEN_CREDENTIALS', 'AzureCliCredential', 'User')
   ```

   Enter the code at `https://microsoft.com/devicelogin`. If your tenant blocks device code sign-in, run `az login` in Bastion instead. The account name must be your workload subscription. The environment variable makes local app calls use your own data roles, not the VM identity. It affects programs started afterward: open VS Code only after this step. Do not set it on App Service.
5. **Refresh the kit clone, once, before creating your work branch:**

   ```powershell
   cd C:\src\factory
   git switch main
   git pull
   ```

   If the folder is missing, ask your team lead before the event or your coach on event days. If they ask you to clone it, use this sparse clone so answer keys and documentation tooling stay out:

   ```powershell
   git clone --no-checkout https://github.com/jonathan-vella/apex-factory-hackathon.git C:\src\factory
   cd C:\src\factory
   git sparse-checkout set --no-cone '/*' '!/coach/' '!/facilitator/' '!/docs/' '!/site/' '!/test/' '!/.vale/' '!/.vale.ini' '!/.markdownlint-cli2.mjs' '!/.prettierignore' '!/prettier.config.mjs' '!/lefthook.yml' '!/package.json' '!/package-lock.json' '!/.node-version' '!/.nvmrc'
   git checkout
   ```

6. **Connect your own repo and create the work branch, once:**

   ```powershell
   cd C:\src\factory
   git remote add member https://github.com/<your-org>/<your-repo>.git
   git switch -c vm-dev01-work
   git push -u member vm-dev01-work
   git remote -v
   git branch -vv
   ```

   `origin` must be the public kit and `member` your own repo. The branch must track `member/vm-dev01-work`. Never push to `origin`, pull the public kit after this setup, or merge this branch into your repo's `main`: their folder layouts differ. See the [branch rules](../../guides/ghcp-upgrade/#save-your-work-and-keep-the-branches-straight).
7. **Clone your own repo separately for evidence:**

   ```powershell
   git clone https://github.com/<your-org>/<your-repo>.git C:\src\<your-repo>
   ```

   This clone stays on `main`. Your imported kit is under `factory/` there; code stays in the separate `C:\src\factory` clone.
8. **Open VS Code on the kit root and sign in to Copilot:**

   ```powershell
   code C:\src\factory
   ```

   Trust the authors when VS Code asks. Choose the **Accounts** icon > **Sign in with GitHub to use GitHub Copilot** and complete browser sign-in. Open the root, not `app/`, so the agent finds `.github/skills/` and `.github/modernization/`.
9. **Configure the Upgrade agent.** In **Extensions**, enable **GitHub Copilot upgrade**; disable **GitHub Copilot modernization** for the workspace if present. In Chat, choose **Local** for **Session Target**, not the remote Copilot coding agent harness. From `F1`, open **MCP: List Servers** > **Upgrade** > **Configure Model Access** and allow the models you will use. Check the agent picker lists **Upgrade**, then send "hello".

### Check your setup

Run in PowerShell 7 on the VM:

```powershell
gh auth status
git config --global user.name
az account show --query name -o tsv
[Environment]::GetEnvironmentVariable('AZURE_TOKEN_CREDENTIALS', 'User')
git -C C:\src\factory remote -v
git -C C:\src\factory branch -vv
git -C C:\src\<your-repo> branch --show-current
git -C C:\src\factory status --short --ignored -- app .github
```

Done when GitHub is signed in, git has your name, Azure shows your workload subscription, the variable is `AzureCliCredential`, the remotes and work-branch upstream match step 6, and the evidence clone is on `main`. The last command prints nothing. VS Code must be open on `C:\src\factory`, with **Upgrade**, **Local** and a Copilot reply to "hello".

If the last command lists leftovers, inspect them before removing files that git does not track, including ignored files from those two folders:

```powershell
cd C:\src\factory
git clean -ndx -- app .github
git clean -fdx -- app .github
```

### Coming back later

Repeat steps 1 and 2 above, open PowerShell 7 and run `code C:\src\factory`; do not repeat clone or branch creation. Read this site in the VM's browser or on your own computer. The app and modernization files are in the kit clone; evidence goes in your private clone on `main`. Restart only when no agent run is active: a restart ends Bastion and interrupts the run. Never stop or deallocate `vm-dev01` during the event.

## 3.4 Save and commit your readiness evidence

`./scripts/Get-PipelineEvidence.ps1` saved `factory/evidence/readiness/test-datacenter.txt` in your dev container and created `.local/<subscription-id>/datacenter.json`. Add your screenshots or exports to `factory/evidence/readiness/`, commit with a conventional message such as `docs: readiness evidence`, and push to `main`. The evidence rule is the same everywhere:

- **Dev container:** evidence goes in `factory/evidence/` on `main`; run `git pull` first.
- **`vm-dev01`:** evidence goes in `C:\src\<your-repo>\factory\evidence\...` (the plain clone of your own repo) on `main`; run `git pull --rebase` first.

Redact subscription, tenant, and object IDs from anything you commit.

### Readiness checklist

Confirm that `factory/evidence/readiness/` in your repository on `main` holds these six items before Step 4 (T-1):

1. **Preflight GO.** The `whatif` **run log**, in the member's **Preflight** step, showing `GO`. WARN rows do not prevent GO; confirm the separate manual checks too.
2. **Datacenter test PASS before Arc.** `evidence/readiness/test-datacenter.txt` with every check PASS.
3. **Arc connected, with the SQL extension.** `vm-app01` showing as **Connected** under **Azure Arc** > **Machines**, and its instance listed under **SQL Server instances** (checked automatically by Step 4 Vending).
4. **Arc migration assessment output.** A screenshot or exported report for `ContosoUniversity`.
5. **Hybrid Benefit and VM state confirmation.** Output or screenshot of `az vm list -g rg-datacenter -d -o table` and `vm-app01`'s `licenseType`.
6. **`vm-dev01` and Copilot working.** A screenshot of Copilot Chat answering in VS Code on `vm-dev01`, saved into `C:\src\<your-repo>\factory\evidence\readiness\` and pushed to `main`.

Let your team lead know as soon as your Step 3 checklist is complete so they know you are ready for [Step 4: Vending (T-1)](../vending/).

## Hints

For deployment, Arc or DNS errors, check [Troubleshooting](../../reference/troubleshooting/).

<details>
<summary>Arc onboarding doesn't finish</summary>

Arc onboarding needs outbound internet through the NAT gateway. Don't rerun `member` after onboarding starts: the stage refuses once `vm-app01` exists as an Arc machine. If onboarding stopped earlier but disabled its guest agent, a rerun instead fails at the datacenter test; that is not a safe repair path. Read the run log, connect through Bastion as in [Switching to vm-dev01](../../guides/ghcp-upgrade/#switching-to-vm-dev01) (use `vm-app01`, same password), and open `C:\LabTools\logs\Connect-AppArc.log` in Notepad.

Check with your team lead first, or follow [If you need to start over](#if-you-need-to-start-over).

</details>

<details>
<summary>Save money between sessions</summary>

Before the event you can stop both VMs when you're not working: `az vm deallocate -g rg-datacenter -n vm-app01`, then the same with `-n vm-dev01`. Running `az vm deallocate` releases the VM's compute and stops its compute billing. Shutting Windows down from inside the VM does not. Bastion, the NAT gateway and the disks bill even when the VMs are stopped.

Start both again before your team lead runs Step 4 at T-1 (`az vm start -g rg-datacenter -n vm-app01`, then `-n vm-dev01`), because vending restarts them and runs the connectivity probes inside them. During the event, never stop `vm-dev01`: it's your workstation.

</details>

## If you need to start over

Before T+2, never run a full, unfiltered `teardown` in the team lead's repo. To recover one member there, pass `-f members=<your index>` to both `teardown` and `member`, or ask your team lead to escalate to the event owner for a coach repair.

- **Before Arc:** in your own repo (member profile), run the `member` stage again to repair the datacenter. In the team lead's repo, add `-f members=<your index>` to the `member` command.
- **After Arc onboarding starts, before C5:** `member` refuses an existing Arc machine; a partially disabled guest agent can instead make the test fail. Do not blindly rerun it. To rebuild with the event owner's approval, run `teardown`, then `member`. In your own repo (member profile), run:

  ```bash
  gh workflow run platform.yml -f stage=teardown
  gh workflow run platform.yml -f stage=member
  ```

  In the team lead's repo, run the same stages with your index:

  ```bash
  gh workflow run platform.yml -f stage=teardown -f members=<your index>
  gh workflow run platform.yml -f stage=member -f members=<your index>
  ```

  Member cleanup removes `rg-datacenter`, `rg-spoke` and the archetype, including the SQL Managed Instance. Repeat Step 3 and the `vm-dev01` setup. If you do not hold eligible Windows Server licenses, add `-f no-hybrid-benefit=true` to the `member` command. If you were already vended, the team lead must run `vending` for your index afterward.

:::caution
After C5, do not use this recovery; member teardown removes the archetype, including the SQL Managed Instance, which takes hours to provision again. Ask the event owner for a coach repair.
:::
