## 4.1 Start all datacenter VMs across the cohort

Both `vm-app01` and `vm-dev01` must be running in every workload subscription before `vending` starts so `vm-app01` reports `Connected` in Azure Arc and the pipeline can restart the VMs and run in-VM connectivity probes.

From `factory/` in `<event>-lead`:

```powershell
$roster = Get-Content .local/roster.json | ConvertFrom-Json
foreach ($m in $roster) {
  az vm start -g rg-datacenter -n vm-app01 --subscription $m.subscriptionId --no-wait
  az vm start -g rg-datacenter -n vm-dev01 --subscription $m.subscriptionId --no-wait
}
```

Wait **about 10 minutes** after the VMs boot, then verify that every slot's `vm-app01` reports `Connected` in Azure Arc:

```powershell
foreach ($m in $roster) {
  $arc = az connectedmachine show -g rg-datacenter -n vm-app01 --subscription $m.subscriptionId --query status -o tsv 2>$null
  [pscustomobject]@{ Index = $m.index; ArcStatus = $arc ?? 'MISSING' }
}
```

Do not start `vending` until every slot in the batch shows `Connected`.

## 4.2 Confirm Entra principal IDs and run `vending`

<Steps>

1. **Confirm `memberPrincipalId` is populated for every slot in `.local/roster.json`.** Vending grants each slot's `memberPrincipalId`:
   - `Owner` on that slot's workload subscription,
   - `Reader` on the shared services subscription, and
   - `Managed Identity Operator` on `id-sqlmi-directory` in `rg-management`.

   If you updated any `memberPrincipalId`, `budgetEmail`, or slot entry in `.local/roster.json` since Step 1, sync the lead pipeline's environment secrets before dispatching `vending`:

   ```powershell
   ./scripts/Initialize-PlatformPipeline.ps1 -RosterPath .local/roster.json
   ```

2. **Dispatch the `vending` stage.**
   - **Up to 50 members:**

     ```bash
     gh workflow run platform.yml -f stage=vending
     ```

   - **More than 50 members:** Phase 1 vends spokes serially so `vnet-hub` peerings and `afwp-hub` rule collection groups never collide, which handles roughly 60 to 70 members inside GitHub Actions' 6-hour (`360`-minute) single-job limit. Dispatch `vending` in batches of up to 50 members—waiting for each batch to finish green before dispatching the next (and check the 90-RCG firewall limit in [Scaling to larger cohorts](/deploy/how-it-works/#scaling-to-larger-cohorts)):

     ```bash
     gh workflow run platform.yml -f stage=vending -f members=1-50
     ```

     Once `1-50` finishes green:

     ```bash
     gh workflow run platform.yml -f stage=vending -f members=51-100
     ```

3. **Monitor the three vending phases and retry if needed.**
   - **Phase 1 (serial readiness check and spoke vending):** verifies `vnet-datacenter` and `vm-app01` Arc `Connected`, moves the subscription under `mg-factory-corp`, builds `rg-spoke`, peers `vnet-spoke` and `vnet-datacenter` to `vnet-hub`, creates `rcg-member-<n>`, applies RBAC and the $500 budget, and sets Foundational CSPM. If Phase 1 stops at an unready slot, fix that slot and re-run the same batch (`vending` is idempotent).
   - **Phase 2 (concurrent VM restart):** restarts `vm-app01` and `vm-dev01` across all vended slots in the batch so both VMs pick up the hub firewall's DNS proxy. If Phase 2 fails, fix the cause and re-run the batch.
   - **Phase 3 (concurrent exemptions and connectivity probes):** records datacenter policy exemptions where required and runs `Test-Connectivity.ps1`. If Phase 3 reports failures only for specific indexes, fix the cause and re-run `vending` for just those indexes:

     ```bash
     gh workflow run platform.yml -f stage=vending -f members=<indexes>
     ```

</Steps>

:::note[Assigning or swapping an attendee after vending]

If an attendee is assigned or swapped after initial vending, update `memberPrincipalId` and `githubUsername` for their slot in `.local/roster.json`, re-run `./scripts/Initialize-PlatformPipeline.ps1 -RosterPath .local/roster.json`, run `gh workflow run platform.yml -f stage=vending -f members=<index>`, and re-run `Initialize-CohortRepos.ps1` for `-MemberIndex <index>`. Because both scripts add permissions idempotently without revoking prior users, **explicitly remove the departing attendee's access**: delete their vending-created Azure role assignments (`Owner` on the workload subscription, `Reader` on shared services, and `Managed Identity Operator` on `id-sqlmi-directory`, or remove them from the slot's Entra group while preserving unrelated pre-existing roles) and remove their collaborator entry under `<org>/<event>-student-<nn>` > **Settings** > **Collaborators**.

:::

## 4.3 Invite students and send private Handoff Cards

Students use the private repositories created in Step 1, including the readiness evidence pushed in Step 3. After vending, the team lead completes the invitations and shares the Handoff Cards; students do not create new repositories.

<Steps>

1. **Collect each attendee's GitHub username.** Ask every attendee for their GitHub handle (for example `octocat`) and fill in `githubUsername` on their assigned slot in `factory/.local/roster.json`.

2. **Verify GitHub organization collaborator and branch settings.** Before sending invites, confirm on your `<org>` settings:
   - **Outside collaborators** are allowed if attendees sign in with personal or external partner GitHub accounts rather than organization-member accounts.
   - **Direct pushes to `main`** are permitted for Write (`push`) collaborators on `<event>-student-*` repositories (no organization rule blocking pushes to `main`).

3. **Send Write collaborator invitations and generate final Handoff Cards.** Run `Initialize-CohortRepos.ps1` from `factory/` in `<event>-lead` (pass `-CoachTeamSlug` or `-CoachUsername` if granting coach Read access):

   ```powershell
   ./scripts/Initialize-CohortRepos.ps1 `
     -RosterPath .local/roster.json `
     -TemplateRepository '<org>/<event>-student-template' `
     -RepoPrefix '<event>-student' `
     -CoachTeamSlug '<existing-coach-team-slug>'
   ```

   For every slot with `githubUsername` set, the script invites the student as a **Write (`push`)** collaborator on `<org>/<event>-student-<nn>` unless they already have Write access, and writes a complete private Handoff Card to `factory/.local/handoff/member-<index>.md`. Ensure coaches have **Read** access to each student repository, using `-CoachTeamSlug`, `-CoachUsername`, or a separate grant. The readiness evidence pushed in Step 3 stays in each existing repository.

4. **Send each student their Handoff Card, assigned Entra sign-in details, and `labadmin` Bastion password privately.** Deliver `factory/.local/handoff/member-<index>.md` over a private direct message or encrypted channel—never in a public channel, issue, or commit—and send them the link to [Student onboarding (before Day 1)](../student-onboarding/).

</Steps>

Done when `vending` is green for all `1..n` slots, each student has a Write invitation or existing Write access and a private Handoff Card, and coaches have Read access to the student repositories.

Next: students complete [Student onboarding (before Day 1)](../student-onboarding/).
